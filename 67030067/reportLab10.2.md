## 5. คำถามและการวิเคราะห์ผลการทดลอง (Lab Questions & Answers)

### ข้อที่ 1: นำผลการ Query `/.well-known/core` มาแสดงในรายงาน พร้อมอธิบายรูปแบบ CoRE Link Format (RFC 6690) ว่าแสดงข้อมูลทรัพยากรอย่างไร
คำตอบ
* **ผลลัพธ์จากการ Query `GET /.well-known/core` ผ่าน CoAP Client:**
  ```text
  </sensor/pot>,</actuator/led>
  การอธิบายรูปแบบ CoRE Link Format (RFC 6690):
รูปแบบ CoRE Link Format (RFC 6690) เป็นมาตรฐานการอธิบายทรัพยากร (Resource Discovery) สำหรับอุปกรณ์ IoT ข้อจำกัดสูง โดยใช้โครงสร้างข้อความแบบเบา (Text-based Web Linking) ดังนี้
1. การระบุ URI Path: แต่ละ Resource จะถูกห่อหุ้มด้วยเครื่องหมายวงเล็บแหลม < > เช่น </sensor/pot> และ </actuator/led>
2. การคั่นรายการ (Delimiter): ใช้เครื่องหมายจุลภาค , คั่นระหว่างแต่ละ Resource ที่ CoAP Server เปิดให้บริการ
3. การต่อเติมคุณลักษณะ (Resource Attributes): สามารถระบุแอตทริบิวต์เพิ่มเติมต่อท้ายด้วยเครื่องหมายอัฒภาค ; เพื่อช่วยในการค้นหา เช่น ประเภทสื่อ (ct=0 สำหรับ text/plain) หรือชนิดอินเทอร์เฟซ (if="sensor")
ประโยชน์: ช่วยให้อุปกรณ์ CoAP Client สามารถทำ Automated Resource Discovery ค้นหาและรับรู้รายการ API ทั้งหมดบนโหนดเซ็นเซอร์ได้ทันทีโดยไม่ต้องรู้อย่างเจาะจงล่วงหน้า

2. อธิบายความแตกต่างของแพ็กเก็ต CoAP ระหว่าง CON (Confirmable) และ NON (Non-confirmable) เมื่อทดสอบในเครือข่ายที่มีการรบกวนสัญญาณ
ตารางเปรียบเทียบระหว่าง CoAP CON และ NON Packets
คำตอบ 

| หัวข้อเปรียบเทียบ | Confirmable (CON) Packet | Non-confirmable (NON) Packet |
| :--- | :--- | :--- |
| **การยืนยันข้อมูล (Acknowledgment)** | **ต้องการ ACK** ตอบกลับจากปลายทางเสมอ | **ไม่ต้องการ ACK** ตอบกลับ (Fire-and-forget) |
| **เมื่อเกิดสัญญาณรบกวน (Packet Loss)** | มีระบบ **Retransmission** ส่งแพ็กเก็ตซ้ำอัตโนมัติ | **ไม่มีการส่งซ้ำ** ข้อมูลที่หล่นหายจะสูญหายทันที |
| **ความน่าเชื่อถือ (Reliability)** | **สูงมาก** การันตีว่าข้อมูล/คำสั่งส่งถึงปลายทางแน่นอน | **ต่ำ** ขึ้นอยู่กับคุณภาพของชั้นเครือข่ายขณะนั้น |
| **ความหน่วงเวลา (Latency)** | สูงกว่า (ต้องรอสัญญาณ ACK และประมวลผลการส่งซ้ำ) | ต่ำมาก (ส่งข้อมูลออกไปทันทีโดยไม่รอคำตอบรับ) |
| **ปริมาณการจราจรบนเครือข่าย** | สร้าง Traffic มากกว่าเนื่องจากมีการส่ง ACK และ Re-send | ประหยัด Bandwidth เครือข่ายมากกว่า |
| **กลไกจัดการความผิดพลาด** | ใช้ Exponential Backoff ในการคำนวณช่วงเวลาส่งซ้ำ | ไม่มีกลไกจัดการความผิดพลาดในระดับ CoAP Layer |
| **สถานการณ์การใช้งานที่เหมาะสม** | คำสั่งที่วิกฤต เช่น สั่งเปิด-ปิดไฟ (`/actuator/led`) | การส่ง Telemetry ความถี่สูง เช่น อ่านค่าเซนเซอร์อนาล็อก |

#### บทวิเคราะห์ผลกระทบเมื่อทดสอบในเครือข่ายที่มีการรบกวนสัญญาณ (Wi-Fi Interference)

1. **กรณีใช้ Confirmable (CON):**  
   เมื่อเกิดสัญญาณรบกวนในชั้นบรรยากาศจนแพ็กเก็ตหล่นหาย ฝั่งส่ง (CoAP Sender) จะไม่ได้รับสัญญาณ ACK ตอบกลับภายในเวลาที่กำหนด (Ack Timeout) ระบบจะทำการ **ส่งแพ็กเก็ตเดิมซ้ำ (Retransmit)** โดยใช้กลไก Exponential Backoff จนกว่าจะได้รับการตอบรับ ทำให้คำสั่งควบคุมฮาร์ดแวร์ยังคงทำงานได้อย่างถูกต้องและมีความแม่นยำสูง

2. **กรณีใช้ Non-confirmable (NON):**  
   หากเกิดสัญญาณรบกวนแล้วแพ็กเก็ตหล่นหาย ข้อมูลชุดนั้นจะสูญหายไปทันทีโดยไม่มีการแจ้งเตือน แต่เนื่องจากถูกออกแบบมาสำหรับการส่งข้อมูลสตรีมมิ่งความถี่สูง (เช่น สตรีมค่า Potentiometer) ระบบจะรอส่งข้อมูลชุดใหม่ในรอบถัดไปแทนการเสียเวลาส่งซ้ำ ช่วยลดปัญหาการจราจรแออัดบนเครือข่าย

วิเคราะห์เมื่อเจอสัญญาณรบกวน:
- CON (Confirmable): หากสัญญาณ Wi-Fi ถูกรบกวนจนแพ็กเก็ตหล่นหาย ฝั่งส่งจะนับเวลา Timeout และ ส่งซ้ำ (Retransmit) โดยใช้กลไก Exponential Backoff จนกว่าจะได้รับ ACK ทำให้คำสั่งควบคุมฮาร์ดแวร์ไม่ผิดพลาด
- NON (Non-confirmable): เหมาะกับการส่งข้อมูลต่อเนื่อง เช่น สตรีมมิ่งค่าเซนเซอร์อนาล็อก หากแพ็กเก็ตหล่นหาย ระบบจะไม่เสียเวลาส่งซ้ำ แต่จะรอส่งข้อมูลรอบถัดไปแทน ช่วยลดภาระจราจรบนเครือข่าย

3. ทำไม CoAP จึงเหมาะสมกับโปรโตคอลการสื่อสารบนเครือข่ายเช่น Thread, Zigbee IP หรือ NB-IoT มากกว่า HTTP?
   คำตอบ
   - Header มีขนาดเล็กมาก (Compact Binary Header):
   CoAP ใช้ Header แบบไบนารีขนาด fixed เพียง 4 ไบต์ (และ Option เพิ่มเติมสั้นๆ) ในขณะที่ HTTP ใช้ Text-based Header ขนาดใหญ่ 200–800 ไบต์ ทำให้ CoAP สามารถบรรจุลงในเฟรมข้อมูลของเครือข่ายที่มี MTU ขนาดเล็กมากได้      อย่าง  พอดี เช่น เครือข่าย 6LoWPAN (IEEE 802.15.4) ใน Thread/Zigbee หรือสัญญาณความถี่แคบของ NB-IoT โดยไม่เกิดการแตกแพ็กเก็ต (Packet Fragmentation)
  - ทำงานบน UDP Transport Layer:
  CoAP ทำงานอยู่บน UDP ทำให้ไม่ต้องเสียเวลาและพลังงานในการสถาปนาการเชื่อมต่อแบบ TCP 3-Way Handshake ช่วยประหยัด RAM และหน่วยประมวลผลของไมโครคอนโทรลเลอร์
  - การประหยัดพลังงานระดับสูง (Low Power / Battery Friendly):
  ด้วยขนาดแพ็กเก็ตที่เล็กและการสื่อสารที่จบได้อย่างรวดเร็ว อุปกรณ์ฝั่งส่งจึงใช้เวลาเปิดภาครับ-ส่งวิทยุน้อยลง ส่งผลให้อุปกรณ์สามารถสลับเข้าสู่โหมดประหยัดพลังงาน (Deep Sleep) ได้นานขึ้น ยืดอายุการใช้งานแบตเตอรี่ได้เป็นปีๆ
  - รองรับ RESTful Architecture และ CoAP Observe (RFC 7641):
  CoAP ยังคงหลักการออกแบบ RESTful (GET, POST, PUT, DELETE) เหมือน HTTP ทำให้เขียนโค้ดง่าย แต่เพิ่มฟีเจอร์ CoAP Observe ที่ทำให้ Server สามารถส่งข้อมูลอัปเดตกลับมายัง Client ได้ทันทีเมื่อค่าเปลี่ยน (Event-driven) โดย   ไม่ต้องใช้วิธี HTTP Polling ที่สิ้นเปลืองพลังงาน
