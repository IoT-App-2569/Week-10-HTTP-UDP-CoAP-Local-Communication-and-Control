### 3. วิเคราะห์ผลและสรุปบทเรียนเชิงวิศวกรรม (Engineering Synthesis)

#### 3.1 เปรียบเทียบจุดเด่นและจุดด้อย (Pros & Cons Matrix)

- **HTTP REST (TCP):**
  - **ข้อดี:** เป็นมาตรฐานสากลที่อุปกรณ์และเว็บบราวเซอร์ทุกประเภท รองรับการพาร์ส JSON ได้ง่าย พัฒนาและเชื่อมต่อกับระบบอื่นได้สะดวกรวดเร็ว
  - **ข้อจำกัด:** มี Header Overhead ขนาดใหญ่ สิ้นเปลือง Bandwidth ความหน่วงเวลาสูงกว่าเนื่องจาก TCP 3-Way Handshake และกินพลังงานแบตเตอรี่มาก
- **UDP Socket:**
  - **ข้อดี:** ความหน่วงเวลา (Latency) ต่ำที่สุด ใช้ทรัพยากร RAM และ CPU บนไมโครคอนโทรลเลอร์น้อยที่สุด โครงสร้างข้อความกระชับ
  - **ข้อจำกัด:** ไม่มีระบบการันตีว่าข้อมูลจะส่งถึงปลายทาง (Unreliable) แพ็กเก็ตอาจหล่นหายโดยไม่รู้ตัว ไม่มีโครงสร้าง API มาตรฐาน (ต้องกำหนดเอง)
- **CoAP (UDP / RFC 7252):**
  - **ข้อดี:** นำข้อดีของสถาปัตยกรรม RESTful (GET, PUT) มารวมกับความเบาของ UDP มี Header ขนาดเล็กเพียง 4 ไบต์ มีระบบการันตีข้อมูลด้วย CON Packet และรองรับ Resource Discovery (`/.well-known/core`)
  - **ข้อจำกัด:** ใช้แรมบนไมโครคอนโทรลเลอร์มากกว่า UDP Raw Socket เนื่องจากมี Context และ Resource Tree ต้องใช้แอปพลิเคชันหรือไลบรารีเฉพาะในการสื่อสาร (เว็บบราวเซอร์ทั่วไปดึงตรงไม่ได้)

#### 3.2 กรณีศึกษาการตัดสินใจเลือกใช้โปรโตคอล (Engineering Case Studies)

- **กรณีศึกษาที่ 1** *ระบบเซนเซอร์วัดความชื้นในดินและวาล์วน้ำเพื่อการเกษตรอัจฉริยะ ทำงานด้วยแบตเตอรี่โซลาร์เซลล์ขนาดเล็ก ติดตั้งกลางแจ้งห่างไกล*
  - **โปรโตคอลที่เลือก:** **CoAP (Constrained Application Protocol)**
  - **เหตุผลทางวิศวกรรม:** อุปกรณ์ใช้พลังงานจากแบตเตอรี่และอาจเชื่อมต่อผ่านเครือข่ายสัญญาณแคบ (เช่น Cellular NB-IoT / Thread) CoAP มี Header ขนาดเล็กเพียง 4 ไบต์ ช่วยประหยัดค่าบริการ Bandwidth และลดระยะเวลาเปิดวิทยุ (Radio Airtime) ทำให้อุปกรณ์เข้าสู่โหมด Deep Sleep ได้เร็วและประหยัดไฟ นอกจากนี้ยังใช้ Confirmable (CON) Packet ในการส่งคำสั่งเปิด-ปิดวาล์วน้ำเพื่อป้องกันความผิดพลาดได้

- **กรณีศึกษาที่ 2** *เว็บแดชบอร์ดสำหรับฝ่ายซ่อมบำรุงในโรงงาน เพื่อเปิดดูสถานะและตั้งค่าพารามิเตอร์ของอุปกรณ์ผ่านเว็บบราวเซอร์บนแท็บเล็ต/สมาร์ตโฟน*
  - **โปรโตคอลที่เลือก:** **HTTP RESTful**
  - **เหตุผลทางวิศวกรรม:** ระบบเน้นความสะดวกในการเข้าถึงจากอุปกรณ์ของผู้ใช้ (แท็บเล็ต/สมาร์ตโฟน) ซึ่งทุกเว็บบราวเซอร์รองรับ HTTP/JSON เป็นมาตรฐานอยู่แล้วโดยไม่ต้องติดตั้งซอฟต์แวร์พิเศษเพิ่มเติม และโครงข่ายในโรงงานมักมีสายไฟและ Wi-Fi ที่มีพลังงานและแบนด์วิดท์เพียงพออยู่แล้ว

- **กรณีศึกษาที่ 3** *ระบบควบคุมแขนกลอุตสาหกรรมความเร็วสูง ที่ต้องการส่งพิกัดตำแหน่งแกนหมุน (X, Y, Z) ด้วยความถี่ 100 ครั้งต่อวินาที (100 Hz) ภายในเครือข่าย LAN ปิด (intranet)*
  - **โปรโตคอลที่เลือก:** **UDP Raw Socket**
  - **เหตุผลทางวิศวกรรม:** การส่งข้อมูลความถี่สูงถึง 100 Hz ต้องการความหน่วงเวลาต่ำสุด (Low Latency) และความแปรปรวนของเวลาต่ำ (Low Jitter) UDP ช่วยให้ยิงพิกัดตำแหน่งออกไปได้ทันทีโดยไม่มี Overhead ของ Handshake หรือ Header ขนาดใหญ่ และการทำงานภายในเครือข่าย LAN ปิดช่วยลดอัตราการสูญหายของแพ็กเก็ตลงได้
