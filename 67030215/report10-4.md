## 4. วิเคราะห์ผลและสรุปบทเรียนเชิงวิศวกรรม (Engineering Synthesis)

### 1. เปรียบเทียบจุดเด่นและจุดด้อย (Pros & Cons Matrix)

* **HTTP** จุดเด่น: เป็นมาตรฐานที่เบราว์เซอร์และเครื่องมืออย่าง curl ใช้ได้ทันที ข้อมูล JSON อ่านง่าย ดีบั๊กง่าย รองรับ TLS และระบบ Proxy/Cache ครบ มีความเชื่อถือได้ในตัวเพราะรันบน TCP จุดด้อย: ภาระส่วนหัวสูง (จากการวัดใน Lab 10.1 Response Header มี 71 ไบต์ ขณะที่ JSON มีเพียง 44 ไบต์ และฝั่ง Request มี Header ใหญ่กว่านั้น) ต้องทำ TCP 3-Way Handshake ทุกการเชื่อมต่อ ใช้แรมมากกว่า UDP (~25–40 KB) และใช้พลังงานและแบนด์วิดท์มากสำหรับอุปกรณ์แบตเตอรี่
* **UDP** จุดเด่น: ภาระส่วนหัวน้อยที่สุด (L7 = 0 ไบต์) ไม่มี Handshake ใช้แรมน้อยที่สุด (~5–10 KB) เขียนง่ายและหน่วงต่ำ เหมาะกับข้อมูลที่ส่งถี่และล้าสมัยเร็ว จุดด้อย: ไม่มีกลไกยืนยันการส่ง การเรียงลำดับ หรือการเข้ารหัสในตัว ต้องออกแบบเอง (เช่น ใส่ Sequence Number และ ACK) Broadcast ข้าม Subnet ไม่ได้ และแพ็กเก็ตอาจสูญหายโดยไม่มีใครรู้
* **CoAP** จุดเด่น: Header เพียง 4 ไบต์ ใช้ UDP จึงเบา แต่ยังมีรูปแบบ REST (GET/PUT/POST) เหมือน HTTP มีทั้งโหมด CON (มี ACK และส่งซ้ำ) และ NON รองรับ Resource Discovery (`/.well-known/core`) และ Observe เหมาะกับเครือข่ายพลังงานต่ำ จุดด้อย: ต้องใช้ไลบรารี libcoap ทำให้ใช้แรมและขนาดเฟิร์มแวร์มากกว่า UDP (~35–50 KB) ต้องตั้งค่า DTLS เพิ่มเมื่อต้องการความปลอดภัย เครื่องมือและการรองรับในเบราว์เซอร์มีน้อยกว่า HTTP และจากการวัดจริงของผม CoAP มีค่า Jitter สูง (42.58 ms) เมื่อใช้งานบนฮอตสปอตมือถือที่มี Wi-Fi Power Save

### 2. กรณีศึกษาการตัดสินใจเลือกใช้โปรโตคอล (Engineering Case Studies)

* **กรณีศึกษาที่ 1** *ระบบเซนเซอร์วัดความชื้นในดินและวาล์วน้ำเพื่อการเกษตรอัจฉริยะ ทำงานด้วยแบตเตอรี่โซลาร์เซลล์ขนาดเล็ก ติดตั้งกลางแจ้งห่างไกล*
  * **โปรโตคอลที่เลือก** CoAP
  * **เหตุผลทางวิศวกรรม** อุปกรณ์ใช้พลังงานจำกัดและมักเชื่อมต่อผ่านเครือข่ายพลังงานต่ำหรือซิมเซลลูลาร์ (เช่น NB-IoT) ซึ่งคิดค่าบริการตามปริมาณข้อมูล CoAP มี Header เพียง 4 ไบต์และไม่ต้องทำ TCP Handshake จึงส่งข้อมูลได้น้อยกว่า HTTP หลายสิบเท่า ลดเวลาเปิดวิทยุและประหยัดแบตเตอรี่ ขณะเดียวกันมีโหมด CON ให้ยืนยันการสั่งเปิด/ปิดวาล์วได้ ซึ่ง UDP ล้วนไม่มี และยังออกแบบให้ใช้รูปแบบ REST (PUT สั่งวาล์ว, GET อ่านความชื้น) ได้ตรงกับงาน

* **กรณีศึกษาที่ 2** *เว็บแดชบอร์ดสำหรับฝ่ายซ่อมบำรุงในโรงงาน เพื่อเปิดดูสถานะและตั้งค่าพารามิเตอร์ของอุปกรณ์ผ่านเว็บบราวเซอร์บนแท็บเล็ต/สมาร์ตโฟน*
  * **โปรโตคอลที่เลือก** HTTP (REST)
  * **เหตุผลทางวิศวกรรม** เบราว์เซอร์ทุกตัวรองรับ HTTP โดยกำเนิด ไม่ต้องติดตั้งแอปหรือไลบรารีเพิ่มบนแท็บเล็ตหรือสมาร์ตโฟน ใช้ JSON แสดงผลและตั้งค่าได้ง่าย มีเครื่องมือดีบั๊ก ระบบยืนยันตัวตนและ TLS (HTTPS) พร้อมใช้ และเนื่องจากเป็นการเปิดดูและตั้งค่าเป็นครั้งคราว ไม่ได้ส่งถี่ และอุปกรณ์ในโรงงานมีไฟเลี้ยงต่อเนื่อง ภาระส่วนหัวที่สูงกว่าจึงไม่ใช่ปัญหาสำคัญ

* **กรณีศึกษาที่ 3** *ระบบควบคุมแขนกลอุตสาหกรรมความเร็วสูง ที่ต้องการส่งพิกัดตำแหน่งแกนหมุน (X, Y, Z) ด้วยความถี่ 100 ครั้งต่อวินาที (100 Hz) ภายในเครือข่าย LAN ปิด (intranet)*
  * **โปรโตคอลที่เลือก** UDP
  * **เหตุผลทางวิศวกรรม** ต้องการความหน่วงต่ำและสม่ำเสมอที่สุดที่ 100 Hz (ทุก 10 ms) UDP ไม่มี Handshake และไม่มีการส่งซ้ำที่ทำให้ข้อมูลใหม่ต้องรอข้อมูลเก่า (Head-of-line blocking แบบ TCP) พิกัดที่ล้าสมัยไม่มีประโยชน์ การทิ้งแพ็กเก็ตเก่าแล้วใช้ค่าล่าสุดจึงดีกว่าการรอส่งซ้ำ ภายใน LAN ปิดอัตราสูญหายต่ำ และภาระส่วนหัวน้อยที่สุด ควรใส่ Sequence Number เพื่อตรวจหาแพ็กเก็ตที่หายและเพิ่มกลไกหยุดฉุกเฉิน (Watchdog/Heartbeat) ที่ระดับแอปพลิเคชันเพื่อความปลอดภัย
