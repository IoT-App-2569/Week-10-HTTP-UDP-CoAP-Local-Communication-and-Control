## 4. วิเคราะห์ผลและสรุปบทเรียนเชิงวิศวกรรม (Engineering Synthesis)

### 1. เปรียบเทียบจุดเด่นและจุดด้อย (Pros & Cons Matrix)

* **HTTP** เด่นที่เบราว์เซอร์และเครื่องมืออย่าง curl ใช้ได้ทันที JSON อ่านง่าย ดีบั๊กง่าย มี TLS และรันบน TCP จึงเชื่อถือได้ในตัว แต่ Header ใหญ่ (Response Header 71 ไบต์ ขณะที่ JSON มีแค่ 44 ไบต์) ต้อง Handshake ทุกการเชื่อมต่อ ใช้แรมมากกว่า UDP (~25–40 KB) และกินพลังงานกับแบนด์วิดท์มาก
* **UDP** เด่นที่ Header น้อยที่สุด (L7 = 0 ไบต์) ไม่มี Handshake ใช้แรมน้อยที่สุด (~5–10 KB) และจากผลวัดจริงมี Mean RTT ต่ำสุด (24.91 ms) แต่ไม่มีการยืนยันการส่ง ไม่เรียงลำดับ ไม่เข้ารหัส แพ็กเก็ตหายได้โดยไม่มีใครรู้ ต้องออกแบบ Sequence Number กับ ACK เอง
* **CoAP** เด่นที่ Header แค่ 4 ไบต์ ใช้ UDP จึงเบา แต่ยังใช้รูปแบบ REST (GET/PUT) แบบ HTTP มีโหมด CON ที่ส่งซ้ำให้อัตโนมัติ รองรับ Discovery และ Observe ข้อเสียคือต้องใช้ libcoap ทำให้ใช้แรมมากกว่า UDP (~35–50 KB) ต้องเพิ่ม DTLS เมื่อต้องการความปลอดภัย เครื่องมือรองรับน้อยกว่า HTTP และจากผลวัดจริงมี Jitter สูงสุด (42.58 ms) เพราะบางรอบตอบช้าผิดปกติ

### 2. กรณีศึกษาการตัดสินใจเลือกใช้โปรโตคอล (Engineering Case Studies)

* **กรณีศึกษาที่ 1** *ระบบเซนเซอร์วัดความชื้นในดินและวาล์วน้ำเพื่อการเกษตรอัจฉริยะ ทำงานด้วยแบตเตอรี่โซลาร์เซลล์ขนาดเล็ก ติดตั้งกลางแจ้งห่างไกล*
  * **โปรโตคอลที่เลือก** CoAP
  * **เหตุผลทางวิศวกรรม** อุปกรณ์มีพลังงานจำกัดและมักใช้เครือข่ายพลังงานต่ำหรือซิมเซลลูลาร์ที่คิดค่าบริการตามปริมาณข้อมูล CoAP ส่งข้อมูลน้อยกว่า HTTP ราว 15–20 เท่า (~13 ไบต์ เทียบกับ ~214–296 ไบต์) และไม่ต้องทำ TCP Handshake จึงเปิดวิทยุสั้นลงและประหยัดแบตเตอรี่ อีกทั้งมีโหมด CON ยืนยันว่าคำสั่งเปิดปิดวาล์วถึงจริง ซึ่ง UDP ล้วนทำไม่ได้

* **กรณีศึกษาที่ 2** *เว็บแดชบอร์ดสำหรับฝ่ายซ่อมบำรุงในโรงงาน เพื่อเปิดดูสถานะและตั้งค่าพารามิเตอร์ของอุปกรณ์ผ่านเว็บบราวเซอร์บนแท็บเล็ต/สมาร์ตโฟน*
  * **โปรโตคอลที่เลือก** HTTP (REST)
  * **เหตุผลทางวิศวกรรม** เบราว์เซอร์ทุกตัวรองรับ HTTP อยู่แล้ว ไม่ต้องติดตั้งแอปหรือไลบรารีเพิ่ม ใช้ JSON แสดงผลและตั้งค่าได้ง่าย มี HTTPS และระบบยืนยันตัวตนพร้อมใช้ งานนี้เปิดดูเป็นครั้งคราวและอุปกรณ์ในโรงงานมีไฟเลี้ยงตลอด Header ที่ใหญ่กว่าจึงไม่เป็นปัญหา

* **กรณีศึกษาที่ 3** *ระบบควบคุมแขนกลอุตสาหกรรมความเร็วสูง ที่ต้องการส่งพิกัดตำแหน่งแกนหมุน (X, Y, Z) ด้วยความถี่ 100 ครั้งต่อวินาที (100 Hz) ภายในเครือข่าย LAN ปิด (intranet)*
  * **โปรโตคอลที่เลือก** UDP
  * **เหตุผลทางวิศวกรรม** ที่ 100 Hz ต้องส่งทุก 10 ms ต้องการความหน่วงต่ำและสม่ำเสมอที่สุด UDP ไม่มี Handshake และไม่มีการส่งซ้ำที่ทำให้ข้อมูลใหม่ต้องรอข้อมูลเก่า พิกัดที่ล้าสมัยไม่มีประโยชน์ ทิ้งแล้วใช้ค่าล่าสุดดีกว่ารอส่งซ้ำ ใน LAN ปิดแพ็กเก็ตหายน้อยอยู่แล้ว ควรใส่ Sequence Number ตรวจแพ็กเก็ตที่หายและเพิ่ม Heartbeat/Watchdog ฝั่งแอปเพื่อหยุดฉุกเฉินเมื่อสัญญาณขาด
