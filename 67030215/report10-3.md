## 4. บันทึกผลการทดลองและคำถามท้ายบท (Lab Report & Questions)
1. นำผลการ Query `/.well-known/core` มาแสดงในรายงาน พร้อมอธิบายรูปแบบ CoRE Link Format (RFC 6690) ว่าแสดงข้อมูลทรัพยากรอย่างไร
```
ผลที่ได้จากข้อ 1 ใน test_coap.py
</sensor/pot>,</actuator/led>

CoRE Link Format (Content-Format 40, application/link-format) คือข้อความธรรมดาที่ Server ใช้ประกาศว่ามีทรัพยากรอะไรบ้าง แต่ละรายการเขียน URI Path ไว้ในเครื่องหมาย < > แล้วคั่นรายการด้วยเครื่องหมายจุลภาค
จากผลลัพธ์ ESP32 มีทรัพยากร 2 ตัว คือ /sensor/pot สำหรับอ่านค่าโพเทนชิโอมิเตอร์ด้วย GET และ /actuator/led สำหรับสั่งเปิดปิดไฟด้วย PUT
ถ้าต้องการบอกรายละเอียดเพิ่ม สามารถต่อ Attribute ท้ายรายการด้วยเครื่องหมาย ; เช่น rt (ชนิดทรัพยากร) if (อินเทอร์เฟซ) ct (ชนิดเนื้อหา) แต่ในการทดลองนี้ไม่ได้กำหนด จึงมีแค่ Path
ทำให้ Client ค้นหาได้เองว่าอุปกรณ์มีอะไรให้เรียกใช้ โดยไม่ต้องรู้ล่วงหน้า
```

2. อธิบายความแตกต่างของแพ็กเก็ต CoAP ระหว่าง CON (Confirmable) และ NON (Non-confirmable) เมื่อทดสอบในเครือข่ายที่มีการรบกวนสัญญาณ
```
CON ผู้รับต้องตอบกลับด้วย ACK ที่มี Message ID ตรงกัน ถ้าผู้ส่งไม่ได้รับ ACK ภายในเวลาที่กำหนด (เริ่มราว 2-3 วินาที) จะส่งซ้ำและเพิ่มเวลารอเป็น 2 เท่าทุกรอบ สูงสุด 4 ครั้ง
ในเครือข่ายที่มีสัญญาณรบกวน ข้อมูลจึงมีโอกาสถึงปลายทางสูง แต่แลกกับความหน่วงที่เพิ่มขึ้นและจำนวนแพ็กเก็ตที่มากขึ้น
สคริปต์ test_coap.py ที่ใช้ aiocoap ส่งคำขอเป็น CON โดยปริยาย เราจึงได้ Response Code 2.05 Content และ 2.04 Changed กลับมายืนยันทุกคำสั่ง

NON ส่งแล้วจบ ไม่มี ACK และไม่ส่งซ้ำ ถ้าแพ็กเก็ตหายระหว่างทางก็หายไปเลย แต่ใช้แบนด์วิธและพลังงานน้อยกว่า
เหมาะกับข้อมูลที่ส่งถี่และค่าใหม่มาแทนค่าเก่าได้ เช่น ค่าเซนเซอร์ ส่วน CON เหมาะกับคำสั่งที่ต้องแน่ใจว่าถึง เช่น สั่งเปิดปิดไฟ
```

3. ทำไม CoAP จึงเหมาะสมกับโปรโตคอลการสื่อสารบนเครือข่ายเช่น Thread, Zigbee IP หรือ NB-IoT มากกว่า HTTP?
```
เครือข่ายเหล่านี้มีแบนด์วิธต่ำ ขนาดแพ็กเก็ตเล็ก (เช่น IEEE 802.15.4 รับได้ราว 127 ไบต์ต่อเฟรม) และอุปกรณ์ใช้แบตเตอรี่
CoAP ทำงานบน UDP มี Header แค่ 4 ไบต์ ไม่ต้องจับมือ 3 ทางแบบ TCP ข้อความทั้งชุดจึงเล็กพอส่งได้ในเฟรมเดียวโดยไม่ต้องแตกแพ็กเก็ต ประหยัดทั้งแบนด์วิธและพลังงาน
ส่วน HTTP ต้องใช้ TCP และมี Header เป็นข้อความขนาดใหญ่ ซึ่งสิ้นเปลืองกว่ามากสำหรับอุปกรณ์เล็ก

CoAP ยังมีความน่าเชื่อถือในตัวผ่าน CON/ACK มีฟีเจอร์ Observe ที่ให้อุปกรณ์แจ้งเมื่อค่าเปลี่ยนโดยไม่ต้องถามซ้ำ และรองรับ Multicast
ขณะที่รูปแบบคำสั่ง GET, PUT, POST, DELETE ยังเหมือน HTTP จึงแปลงเชื่อมกับเว็บผ่าน Proxy ได้ง่าย
```
