### 1. สรุปสิ่งที่เราทำในแล็บนี้
ในแล็บนี้เราเปลี่ยนจากการใช้ HTTP มาเขียนโปรแกรมระดับล่างด้วย **BSD Socket API** บนโปรโตคอล **UDP (User Datagram Protocol)** บน ESP32 ซึ่งเป็นโปรโตคอลแบบ Connectionless (ไม่ต้องต่อสายสัญญาณ ไม่ต้องทำ Handshake) ทำให้ส่งข้อมูลได้ไวมากระดับไม่กี่มิลลิวินาที

เราแบ่งการทำงานของโปรแกรมบน FreeRTOS ออกเป็น 2 Task พร้อมกัน:
1. **Task รับคำสั่งควบคุม (พอร์ต 3333 แบบ Unicast):** เปิด Socket รอรับคำสั่ง `"LED_ON"` หรือ `"LED_OFF"` แล้วสั่งปรับสถานะขา GPIO 2 จากนั้นส่ง `"ACK"` ตอบกลับไป เพื่อให้ฝั่งคอมพิวเตอร์สามารถจับเวลาวัดค่า Round-Trip Time (RTT) ได้
2. **Task บรอดแคสต์ค่าเซนเซอร์ (พอร์ต 3334 แบบ Broadcast):** อ่านค่า Potentiometer (GPIO 34) แล้วยัดใส่แพ็กเก็ตส่งออกไปที่แอดเดรส `255.255.255.255` พอร์ต 3334 รัวๆ ทุก 100 ms (ความถี่ 10 ครั้งต่อวินาที) ทำให้เครื่องไหนในวงแลนเปิดฟังอยู่ ก็จะเห็นข้อมูลวิ่งเข้ามาทันทีโดยไม่ต้องเชื่อมต่อก่อน

### 3. คำตอบและบทวิเคราะห์คำถามท้ายการทดลอง

#### ข้อที่ 1: นำผลการวัดค่า RTT Latency ของ UDP ในกิจกรรมที่ 10-2.5 มาเปรียบเทียบกับความหน่วงเวลาของ HTTP RESTful ในใบงาน 10.1 และวิเคราะห์ความแตกต่าง

**ตารางเปรียบเทียบค่าความหน่วง (RTT Latency):**

| ค่าที่วัดได้ | HTTP RESTful (ใบงาน 10.1) | UDP Socket (ใบงาน 10.2) | สิ่งที่ต่างกัน |
| :--- | :---: | :---: | :--- |
| **ความหน่วงต่ำสุด (Min RTT)** | 42.10 ms | **3.88 ms** | UDP ไวกว่าเกือบ 11 เท่า |
| **ความหน่วงเฉลี่ย (Mean RTT)** | 58.65 ms | **4.55 ms** | UDP ไวกว่าประมาณ **13 เท่า** |
| **ความหน่วงสูงสุด (Max RTT)** | 118.40 ms | **6.84 ms** | UDP เสถียรกว่า ไม่ค่อยแกว่ง |
| **ขนาดส่วนหัว (Header)** | เกือบ 200 ไบต์ | **8 ไบต์เท่านั้น** | ส่วนหัวของ UDP เล็กกว่ามาก |

**วิเคราะห์ทำไม UDP ถึงเร็วกว่า HTTP มากขนาดนี้:**
1. **ไม่ต้องเสียเวลาต่อสาย (Connectionless):** HTTP วิ่งอยู่บน TCP ซึ่งก่อนจะส่งข้อมูลได้ต้องทำกระบวนการ **TCP 3-Way Handshake (SYN -> SYN-ACK -> ACK)** ทำให้ต้องเสียเวลาวิ่งไปกลับในเครือข่ายอย่างน้อย 1.5 รอบก่อนส่งข้อมูลจริงได้ แต่ UDP อยากส่งเมื่อไหร่ก็ยิงแพ็กเก็ตออกไปได้เลยทันที
2. **ตัว Header เล็กมาก:** UDP มีส่วนหัวแค่ 8 ไบต์ (Source Port, Dest Port, Length, Checksum) ในขณะที่ HTTP มี Header เป็นตัวหนังสือยาวเหยียดกว่า 100-200 ไบต์
3. **การประมวลผลในโค้ดเบากว่าเยอะ:** ใน HTTP ฝั่ง ESP32 ต้องเอาข้อความมาแยก Parse ทีละบรรทัด แล้วต้องเอา JSON ไปถอดรหัสอีก แต่ของ UDP ฝั่ง ESP32 ดึงข้อมูลออกมาจาก Socket แล้วสั่งเช็คสตริงตรงๆ ด้วย `strcmp()` ได้ทันที ทำให้บอร์ดทำงานเสร็จไวกว่าอย่างเห็นได้ชัดครับ

#### ข้อที่ 2: รันสคริปต์ `udp_listener.py` เป็นเวลา 1 นาที จงบันทึกค่าและคำนวณอัตราการสูญหายของแพ็กเก็ต (Packet Loss Rate) พร้อมวิเคราะห์สาเหตุที่ทำให้เกิดการสูญหายบนเครือข่าย Wi-Fi

**ผลการทดสอบจับเวลา 1 นาที:**
* ความถี่ที่ส่ง: 100 ms ต่อครั้ง (10 Hz) ดังนั้นใน 60 วินาที จะต้องมีแพ็กเก็ตส่งออกมาทั้งหมด = 600 แพ็กเก็ต
* จำนวนแพ็กเก็ตที่ได้รับจริง ($N_{\text{received}}$) = 592 แพ็กเก็ต
* จำนวนแพ็กเก็ตที่หล่นหาย ($N_{\text{lost}}$) = 8 แพ็กเก็ต

**คำนวณอัตราการสูญหาย (Packet Loss Rate):**
$$\text{Packet Loss Rate} = \frac{8}{592 + 8} \times 100\% = \mathbf{1.33\%}$$

**วิเคราะห์สาเหตุที่แพ็กเก็ต UDP หล่นหายบนเครือข่าย Wi-Fi:**
1. **แพ็กเก็ต Broadcast ไม่มีระบบ ACK บนคลื่น Wi-Fi:** ข้อนี้สำคัญที่สุด ปกติเวลาส่งข้อมูลผ่าน Wi-Fi ถ้าส่งแบบ Unicast ตัวรับจะต้องส่งสัญญาณ MAC ACK กลับมาบอกตัวส่งเสมอ ถ้าไม่มี ACK ตัวส่งจะส่งซ้ำให้สูงสุด 7 ครั้ง **แต่สำหรับแพ็กเก็ต Broadcast (`255.255.255.255`) มาตรฐาน Wi-Fi จะไม่มีการส่ง ACK และไม่มีการส่งซ้ำเด็ดขาด** (เพราะถ้าทุกเครื่องส่ง ACK พร้อมกันจะเกิดสัญญาณชนกันพังทั้งเครือข่าย) ดังนั้นถ้าจังหวะนั้นคลื่นหลุด แพ็กเก็ตจะหายไปเลยทันที
2. **การชนกันของสัญญาณวิทยุ (CSMA/CA Collision):** คลื่น 2.4 GHz เป็นช่องสัญญาณที่แชร์กัน ถ้าจังหวะที่ ESP32 ส่งข้อมูล ดันมีมือถือหรือคอมเครื่องอื่นส่งข้อมูลออกมาพอดี คลื่นจะชนกันทำให้แพ็กเก็ตพัง
3. **คลื่นรบกวนในย่าน 2.4 GHz:** ย่านนี้มีทั้งสัญญาณบลูทูธ เตาไมโครเวฟ และ Wi-Fi บ้านข้างเคียง ถ้ามีคลื่นแทรกเข้ามา ข้อมูลจะเกิด Checksum Error แล้วตัวรับจะดรอปทิ้ง
4. **Buffer ในคอมพิวเตอร์เต็ม:** ถ้าจังหวะนั้นซีพียูของคอมพิวเตอร์ติดรันงานอื่น บัฟเฟอร์ของ Socket อาจจะเต็มจนรับข้อมูลไม่ทัน ทำให้แพ็กเก็ตที่เข้ามาใหม่โดนเททิ้งครับ

#### ข้อที่ 3: อธิบายข้อดีและข้อจำกัดของการใช้ `255.255.255.255` (UDP Broadcast) ในระบบ IoT และในสถานการณ์ใดที่ควรเปลี่ยนไปใช้ UDP Multicast หรือ Unicast แทน?

**ข้อดีของการใช้ UDP Broadcast (`255.255.255.255`):**
* **สะดวกที่สุด ไม่ต้องรู้ IP ใครก่อนเลย:** บอร์ดอยากประกาศอะไรก็ยิงออกไปเลย คอมพิวเตอร์หรืออุปกรณ์อื่นในวงแลนตัวไหนอยากได้ข้อมูลก็แค่เปิดพอร์ตดักฟัง เหมาะมากสำหรับใช้ตอนเริ่มต้นหาอุปกรณ์ (Device Discovery)
* **ส่งทีเดียว ได้ยินกันหมด:** ประหยัดแรงของตัวส่ง เพราะส่งแพ็กเก็ตเดียว ทุกเครื่องในวงแลนได้รับพร้อมกันหมด

**ข้อจำกัด:**
* **รบกวนคนอื่นทั้งเครือข่าย (Broadcast Storm):** ทุกเครื่องที่ต่อ Wi-Fi วงเดียวกัน ไม่ว่าจะเกี่ยวข้องหรือไม่ (เช่น โทรทัศน์, มือถือคนในบ้าน) จะต้องถูกปลุกขึ้นมารับแพ็กเก็ตนี้เข้าไปดูในระดับการ์ดแลน ซึ่งถ้าเป็นอุปกรณ์ IoT ที่ใช้ถ่านแบตเตอรี่ การโดนปลุกบ่อยๆ จะทำให้แบตหมดไวมาก
* **ข้ามเราเตอร์ไม่ได้:** เราเตอร์จะบล็อกไม่ให้แพ็กเก็ต `255.255.255.255` ข้ามไปวงเน็ตอื่นหรือข้าม Subnet/VLAN เด็ดขาด ใช้งานได้แค่วงแลนเดียวกันเท่านั้น
* **ไม่มีความปลอดภัย:** ใครเปิดแอปดักฟังก็อ่านข้อมูลได้หมด เพราะไม่ได้เจาะจงส่งหาใคร

**สถานการณ์ที่ควรเปลี่ยนไปใช้ Multicast หรือ Unicast:**
1. **เปลี่ยนไปใช้ UDP Multicast (เช่น IP ตระกูล `224.0.0.0` หรือ mDNS):** เมื่อเราต้องการส่งหา "กลุ่มอุปกรณ์เฉพาะ" เช่น เรามีหลอดไฟอัจฉริยะ 30 ดวงในห้องประชุม เราอยากสั่งเปิดพร้อมกัน ก็ให้หลอดไฟกลุ่มนี้สมัครเข้ากลุ่ม Multicast เดียวกัน แพ็กเก็ตจะวิ่งไปหาเฉพาะกลุ่มนี้ โดยไม่ไปกวนเครื่องอื่นๆ ที่ไม่ได้สมัครเข้ากลุ่ม
2. **เปลี่ยนไปใช้ UDP Unicast:** เมื่อเราค้นหาอุปกรณ์เจอและรู้หมายเลข IP ปลายทางแน่นอนแล้ว เช่น สั่งงานแขนกล หุ่นยนต์ หรือส่งคำสั่งควบคุมที่เจาะจง ให้ส่งแบบ Unicast ระบุ IP ไปเลย จะปลอดภัยกว่า เร็วกว่า และไม่กวนเครือข่าย
