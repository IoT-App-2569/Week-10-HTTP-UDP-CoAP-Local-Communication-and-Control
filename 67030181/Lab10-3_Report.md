# รายงานผลการทดลอง ใบงานที่ 10.3
## เรื่อง: การสร้าง CoAP Server บน ESP32 และการควบคุมอุปกรณ์ด้วยโปรโตคอลน้ำหนักเบาสำหรับ IoT

* **รหัสนักศึกษา:** 67030181
* **วิชาปฏิบัติการ:** ระบบควบคุมและสื่อสารไอโอที (IoT Communication & Control)
* **โฟลเดอร์โค้ด:** `67030181/Lab10-3_CoAP_Server/`

---

### 1. สรุปสิ่งที่เราทำในแล็บนี้
ในแล็บนี้เราได้ลองใช้โปรโตคอล **CoAP (Constrained Application Protocol - RFC 7252)** ซึ่งเป็นโปรโตคอลที่เอาข้อดีของ 2 ขั้วมารวมกัน คือ:
* มีแนวคิดแบบ **RESTful (GET, PUT, POST, DELETE)** เหมือน HTTP ทำให้แบ่งทรัพยากรเป็นโฟลเดอร์เข้าใจง่าย
* แต่วิ่งอยู่บน **UDP** และมีขนาด Header คงที่เพียง **4 ไบต์เท่านั้น** ทำให้เบาและกินพลังงานต่ำมาก เหมาะกับอุปกรณ์ฝังตัวตัวเล็กๆ หรือพวกที่ใช้แบตเตอรี่

ในการทดลองนี้ เราใช้คอมโพเนนต์ `espressif/coap` (`libcoap`) บน ESP-IDF แล้วสร้าง Endpoint ขึ้นมา 3 ตัว:
1. `/.well-known/core` (GET): ไดเรกทอรีกลางสำหรับให้อุปกรณ์อื่นมาถามว่าบอร์ดนี้ทำอะไรได้บ้าง
2. `/sensor/pot` (GET): อ่านค่าแรงดันแอนะล็อกของตัวต้านทานปรับค่าได้ (GPIO 34)
3. `/actuator/led` (PUT): สั่งเปิด-ปิดไฟ LED ที่ขา GPIO 2 ด้วยการส่งตัวเลข `'1'` หรือ `'0'`

---

### 2. ผลการทดสอบการทำงาน

เราใช้สคริปต์ Python ร่วมกับไลบรารี `aiocoap` ในไฟล์ `test_coap.py` เพื่อยิงคำสั่งเข้าไปทดสอบบอร์ด ESP32:
```powershell
python test_coap.py 192.168.1.181
```

**ผลลัพธ์ที่ได้บน Terminal:**
```text
--- 1. ทดสอบ CoAP Resource Discovery (/.well-known/core) ---
รายการ Resource ทั้งหมดที่พบบนบอร์ด (CoRE Link Format):
</sensor/pot>;rt="sensor";if="sensor",</actuator/led>;rt="actuator";if="control"

--- 2. ทดสอบ CoAP GET /sensor/pot ---
ค่าเซนเซอร์ Potentiometer ที่อ่านได้: 1845 (รหัสสถานะ: 2.05 Content)

--- 3. ทดสอบ CoAP PUT /actuator/led (สั่งเปิดไฟ) ---
สถานะตอบกลับหลังสั่งเปิดไฟ: 2.04 Changed
(ไฟ LED ที่ขา GPIO 2 ติดสว่างขึ้น)

--- 4. ทดสอบ CoAP PUT /actuator/led (สั่งปิดไฟ) ---
สถานะตอบกลับหลังสั่งปิดไฟ: 2.04 Changed
(ไฟ LED ที่ขา GPIO 2 ดับลง)
```
การทำงานตอบสนองได้ถูกต้อง รหัสสถานะ `2.05 Content` เทียบเท่ากับ `200 OK` ใน HTTP และรหัส `2.04 Changed` เทียบเท่ากับการอัปเดตสถานะสำเร็จ และหลอดไฟ LED บนบอร์ดก็ติด/ดับตามคำสั่งทันที

### 3. คำตอบและบทวิเคราะห์คำถามท้ายการทดลอง

#### ข้อที่ 1: นำผลการ Query `/.well-known/core` มาแสดงในรายงาน พร้อมอธิบายรูปแบบ CoRE Link Format (RFC 6690) ว่าแสดงข้อมูลทรัพยากรอย่างไร

**ผลลัพธ์ที่ได้จากการดึง `/.well-known/core`:**
```text
</sensor/pot>;rt="sensor";if="sensor",</actuator/led>;rt="actuator";if="control"
```

**อธิบายรูปแบบ CoRE Link Format (RFC 6690):**
CoRE Link Format เป็นรูปแบบข้อความมาตรฐานสากลที่ออกแบบมาเพื่อให้อุปกรณ์ IoT คุยกันเองได้แบบ **Machine-to-Machine (M2M)** โดยที่ฝั่ง Client ไม่จำเป็นต้องรู้ล่วงหน้าว่าบอร์ดมี URL อะไรบ้าง แค่ยิงมาถามที่ `/.well-known/core` บอร์ดก็จะตอบกลับมาเป็นรายการทรัพยากรทั้งหมด

**โครงสร้างข้อความ:**
1. **ชื่อ Resource:** จะอยู่ในเครื่องหมายวงเล็บแหลม เช่น `</sensor/pot>` หรือ `</actuator/led>`
2. **การคั่นแต่ละตัว:** ถ้ามีหลาย Resource จะคั่นด้วยเครื่องหมายจุลภาค (Comma `,`)
3. **พารามิเตอร์บอกคุณสมบัติ (Attributes):** จะเขียนต่อท้าย URL โดยคั่นด้วยเครื่องหมาย Semicolon (`;`) เช่น:
   * `rt="sensor"`: ย่อมาจาก **Resource Type** บอกว่า URL นี้เป็นเซนเซอร์นะ หรือถ้าเป็น `rt="actuator"` ก็บอกว่าเป็นตัวสั่งงานอุปกรณ์
   * `if="sensor"` หรือ `if="control"`: ย่อมาจาก **Interface Description** บอกลักษณะการใช้งาน เช่น เป็นแบบอ่านค่าอย่างเดียว (Read-only) หรือเป็นแบบควบคุมสั่งงาน (Control)
   * ถ้ามีระบบแจ้งเตือนอัตโนมัติ (Observe) ก็จะพ่วง attribute `obs` เข้ามาด้วย ทำให้ระบบอื่นอ่านแล้วรู้ได้ทันทีว่า Resource นี้มีฟังก์ชันอะไรบ้างโดยไม่ต้องมีคนมาคอยบอกครับ

#### ข้อที่ 2: อธิบายความแตกต่างของแพ็กเก็ต CoAP ระหว่าง CON (Confirmable) และ NON (Non-confirmable) เมื่อทดสอบในเครือข่ายที่มีการรบกวนสัญญาณ

**ความแตกต่างหลักระหว่าง 2 แบบ:**

| คุณสมบัติ | Confirmable (CON) | Non-confirmable (NON) |
| :--- | :--- | :--- |
| **การตอบรับ** | ผู้รับ **ต้องส่ง ACK กลับมาเสมอ** | **ไม่ต้องส่ง ACK** ส่งแล้วจบเลย (Fire-and-forget) |
| **การส่งซ้ำเมื่อหลุด** | **มีระบบส่งซ้ำอัตโนมัติ** ถ้าไม่ได้ ACK | **ไม่มีการส่งซ้ำ** หายแล้วหายเลย |
| **ความน่าเชื่อถือ** | สูงมาก ข้อมูลไม่ตกหล่น | ปานกลาง ขึ้นอยู่กับสภาพคลื่นวิทยุ |
| **ความหน่วง (Latency)** | ถ้าสัญญาณดีจะไว แต่ถ้าหลุดจะช้าเพราะต้องรอ Timeout | ไวคงที่เสมอ ไม่มีจังหวะสะดุด |
| **งานที่เหมาะสม** | คำสั่งสำคัญ เช่น สั่งเปิด-ปิดไฟ, ปลดล็อกประตู | การส่งข้อมูลเซนเซอร์ที่ส่งบ่อยๆ เช่น วัดอุณหภูมิทุก 3 วิ |

**วิเคราะห์เมื่อทดสอบในเครือข่ายที่มีคลื่นรบกวน:**
* **แบบ CON:** เวลาที่มีสัญญาณกวนจนแพ็กเก็ตหล่นหาย ตัวส่ง CoAP จะจับเวลา Timeout (ค่าเริ่มต้น 2 วินาที) ถ้ายังไม่ได้ยิน ACK กลับมา มันจะทำการ **ส่งซ้ำ (Retransmit)** ด้วยเลข Message ID เดิม และจะขยายเวลาเป็น 4 วินาที (Exponential Backoff) ทำให้คำสั่งเปิด-ปิดไฟของเรายังคงทำงานได้แน่นอน 100% เพียงแต่อาจจะเห็นความหน่วงกระโดดขึ้นไปเป็น 2 วินาทีในจังหวะที่มีสัญญาณรบกวน
* **แบบ NON:** ข้อมูลจะวิ่งออกไปขาเดียว ถ้าโดนคลื่นกวน ข้อมูลค่าเซนเซอร์รอบนั้นก็จะแหว่งหายไปเลย แต่ข้อดีคือระบบจะไม่ต้องค้างรอ Timeout ข้อมูลรอบถัดไปก็จะถูกส่งต่อทันทีโดยไม่สะดุดครับ

#### ข้อที่ 3: ทำไม CoAP จึงเหมาะสมกับโปรโตคอลการสื่อสารบนเครือข่ายเช่น Thread, Zigbee IP หรือ NB-IoT มากกว่า HTTP?

**เหตุผลสำคัญทางวิศวกรรม:**
1. **ขนาดของเฟรมข้อมูลในคลื่นวิทยุจำกัดมาก (MTU เล็ก):**
   * เครือข่ายไร้สายพลังงานต่ำอย่าง Thread และ Zigbee (มาตรฐาน IEEE 802.15.4) รองรับขนาดแพ็กเก็ตสูงสุดได้แค่ **127 ไบต์เท่านั้น**
   * ลำพังแค่ Header ของ HTTP อย่างเดียวก็ปาเข้าไป 200-500 ไบต์แล้ว ถ้าจะส่งผ่าน HTTP แพ็กเก็ตจะต้องถูกหั่นแตกกระจาย (Fragmentation) เป็น 4-5 ชิ้น ซึ่งทำให้สิ้นเปลืองและเสี่ยงต่อการหลุดหายสูงมาก
   * แต่ CoAP มี Header ขนาดคงที่แค่ **4 ไบต์** เท่านั้น สามารถยัดลงในเฟรม 127 ไบต์ได้สบายๆ ในแพ็กเก็ตเดียว จบได้ในรอบเดียว
2. **ประหยัดแบตเตอรี่ (กินไฟน้อยกว่าเยอะ):**
   * HTTP บังคับใช้ TCP ซึ่งต้องทำ Handshake ไป-กลับหลายรอบก่อนเริ่มส่งข้อมูล ทำให้ชิปวิทยุต้องเปิดคอยรับส่งข้อมูลอยู่นาน (กินไฟเยอะ)
   * CoAP ทำงานบน UDP ยิงแพ็กเก็ตเสร็จ ชิปไมโครคอนโทรลเลอร์สามารถสั่งเข้าโหมด **Deep Sleep (หลับลึก)** ได้ทันทีในเวลาไม่ถึง 20 มิลลิวินาที ทำให้อุปกรณ์ที่ใส่ถ่านกระดุมก้อนเล็กๆ อยู่ได้ยาวนานหลายปี
3. **ฟังก์ชัน Observe ประหยัดค่าเน็ต SIM (NB-IoT):**
   * ใน HTTP ถ้าเราอยากรู้ค่าเซนเซอร์ เราต้องสั่ง Polling ยิง `GET` ไปถามทุกๆ 1 วินาที ซึ่งถ้าใช้ซิม NB-IoT จะเปลืองค่าเน็ตและแบตหมดไวมาก
   * ใน CoAP มีระบบ **Observe (RFC 7641)** ที่ฝั่ง Client ขอติดตามไว้ครั้งเดียว แล้วตัว ESP32 จะเป็นฝ่าย Push ข้อมูลส่งกลับมาให้เฉพาะตอนที่ค่าเซนเซอร์เปลี่ยนเท่านั้น ช่วยประหยัดแบนด์วิดท์ได้เกิน 90
