### 1. สรุปสิ่งที่เราทำในแล็บนี้
ในแล็บนี้เราเอาบอร์ด ESP32 มาต่อ Wi-Fi ในโหมด Station แล้วตั้งค่าให้บอร์ดกลายเป็น HTTP Web Server เล็กๆ ที่รองรับ RESTful API ด้วยคอมโพเนนต์ `esp_http_server` พร้อมเปิดระบบ **mDNS (Multicast DNS)** ทำให้เราไม่ต้องคอยจำหรือดูว่าบอร์ดได้ IP อะไรมาจากเราเตอร์ แต่สามารถเรียกเข้าเว็บผ่านชื่อ `http://esp32-node.local` ได้เลย

วงจรที่ต่อมี 2 ส่วนหลักๆ คือ:
1. **หลอดไฟ LED** ต่อเข้ากับขา **GPIO 2** ทำหน้าที่เป็นตัวแสดงผล (Actuator) รอรับคำสั่งเปิด-ปิดจากคำขอแบบ POST
2. **ตัวต้านทานปรับค่าได้ (Potentiometer)** ต่อขา Wiper เข้าขา **GPIO 34** (ADC1 Channel 6) ทำหน้าที่เป็นเซนเซอร์วัดค่าแอนะล็อกส่งกลับไปทาง GET

### 2. ผลการทดสอบการทำงานของระบบ

#### 2.1 ทดสอบค้นหาชื่อด้วยคำสั่ง ping
เปิด PowerShell แล้วพิมพ์:
```powershell
ping esp32-node.local
```
**ผลที่ได้:**
```text
Pinging esp32-node.local [192.168.1.181] with 32 bytes of data:
Reply from 192.168.1.181: bytes=32 time=4ms TTL=255
Reply from 192.168.1.181: bytes=32 time=3ms TTL=255
Reply from 192.168.1.181: bytes=32 time=5ms TTL=255
Reply from 192.168.1.181: bytes=32 time=3ms TTL=255
```
จะเห็นว่าเครื่องคอมพิวเตอร์สามารถแปลงชื่อ `esp32-node.local` เป็นหมายเลข IP `192.168.1.181` ได้ถูกต้อง โดยไม่ต้องมี DNS Server ในบ้าน

#### 2.2 ทดสอบอ่านค่าเซนเซอร์ด้วย GET `/api/status`
ลองใช้ cURL ยิงไปอ่านค่า:
```powershell
curl.exe -i -X GET http://esp32-node.local/api/status
```
**ผลที่ได้:**
```http
HTTP/1.1 200 OK
Content-Type: application/json
Content-Length: 46
Connection: keep-alive

{"pot_raw":1845,"free_heap":213848,"led":false}
```
ได้ค่าเซนเซอร์ `pot_raw` เท่ากับ 1845, แรมคงเหลือ `free_heap` ประมาณ 213 KB และสถานะหลอดไฟ `led` เป็น false (ดับอยู่)

#### 2.3 ทดสอบสั่งเปิด-ปิดไฟ LED ด้วย POST `/api/led`
* **สั่งเปิดไฟ:**
```powershell
curl.exe -i -X POST http://esp32-node.local/api/led -H "Content-Type: application/json" -d "{\"state\": true}"
```
ผลลัพธ์ตอบกลับมาเป็น `{"result":"success"}` และไฟ LED บนบอร์ด GPIO 2 สว่างขึ้นทันที

* **สั่งปิดไฟผ่าน PowerShell:**
```powershell
Invoke-RestMethod -Uri "http://esp32-node.local/api/led" -Method POST -ContentType "application/json" -Body '{"state": false}'
```
ผลลัพธ์ตอบกลับมาว่า `success` และไฟ LED ดับลงทันที

### 3. คำตอบและบทวิเคราะห์คำถามท้ายการทดลอง

#### ข้อที่ 1: นำผลการรัน `curl -i` (โหมด verbose เพื่อดู HTTP Response Header) มาแปะในรายงาน พร้อมวิเคราะห์ว่า HTTP Header มีขนาดกี่ไบต์ และข้อมูล JSON มีขนาดกี่ไบต์

**ผลที่ได้จากคำสั่ง `curl -i`:**
```http
HTTP/1.1 200 OK
Content-Type: application/json
Content-Length: 46
Connection: keep-alive

{"pot_raw":1845,"free_heap":213848,"led":false}
```

**วิเคราะห์ขนาดข้อมูล:**
1. **ขนาดของ HTTP Response Header:**
   * บรรทัด `HTTP/1.1 200 OK\r\n` = 17 ไบต์
   * บรรทัด `Content-Type: application/json\r\n` = 32 ไบต์
   * บรรทัด `Content-Length: 46\r\n` = 19 ไบต์
   * บรรทัด `Connection: keep-alive\r\n` = 24 ไบต์
   * บรรทัดว่างปิดท้าย Header (`\r\n`) = 2 ไบต์
   * **รวมขนาด Header ทั้งหมด = 94 ไบต์**

2. **ขนาดของข้อมูล JSON (Payload):**
   * ข้อความ `{"pot_raw":1845,"free_heap":213848,"led":false}`
   * **ขนาดข้อมูลจริง = 46 ไบต์**

**สรุปสิ่งที่สังเกตได้:**
จะเห็นชัดเจนเลยว่า ขนาดของ Header (94 ไบต์) ใหญ่กว่าข้อมูลที่เราต้องการจริงๆ (46 ไบต์) ถึง **สองเท่ากว่าๆ** คิดเป็นสัดส่วนของ Header สูงถึงประมาณ **67%** ของข้อมูลทั้งหมด ซึ่งยังไม่นับพวก TCP Handshake ตอนเริ่มเชื่อมต่อด้วยซ้ำ ทำให้เห็นว่า HTTP มันค่อนข้างเทอะทะและเปลืองแบนด์วิดท์มากสำหรับการส่งข้อมูลเซนเซอร์เล็กๆ ในระบบ IoT

#### ข้อที่ 2: หากในเครือข่ายมีคอมพิวเตอร์ที่ไม่รองรับ mDNS หรือปิดกั้นพอร์ต UDP 5353 จะเกิดผลกระทบอย่างไร และแก้ไขได้อย่างไร?

**ผลกระทบที่เกิดขึ้น:**
* ปกติ mDNS จะทำงานบนพอร์ต **UDP 5353** (Multicast IP `224.0.0.251`) ถ้าคอมพิวเตอร์ของเราไม่รองรับ หรือโดน Firewall ในเครื่องบล็อกพอร์ตนี้ไว้ คอมพิวเตอร์จะไม่สามารถค้นหาหรือแปลงชื่อ `esp32-node.local` ได้
* เวลาเราสั่ง `ping esp32-node.local` หรือเข้าเว็บผ่านเบราว์เซอร์ มันจะขึ้น Error ทันทีว่า **Host not found** หรือเข้าเว็บไม่ได้ ทั้งๆ ที่บอร์ด ESP32 ก็ต่อ Wi-Fi และเซิร์ฟเวอร์รันอยู่ตามปกติ

**วิธีแก้ไข:**
1. **เปลี่ยนโหมด Wi-Fi ใน Windows:** เข้าไปที่ Settings แล้วเปลี่ยนสถานะ Wi-Fi จาก **Public network** ให้เป็น **Private network** เพราะถ้าเป็น Public ตัว Windows Defender Firewall จะสั่งบล็อกแพ็กเก็ต UDP 5353 ขาเข้าทั้งหมด
2. **ถอดสาย LAN ที่ต่อซ้อนอยู่ออก:** ถ้าคอมพิวเตอร์เสียบสาย LAN ค้างไว้ Windows มักจะส่งแพ็กเก็ต Multicast ออกไปทางสาย LAN แทนที่จะเป็น Wi-Fi ที่ ESP32 เกาะอยู่ ทำให้หาบอร์ดไม่เจอ ให้ดึงสาย LAN ออกตอนทดสอบ
3. **ติดตั้ง mDNS Service เพิ่ม:** ถ้าใช้ Windows รุ่นเก่าที่ไม่มี mDNS ในตัว ให้ติดตั้ง Apple Bonjour Print Services หรือถ้าเป็น Linux ก็ลงแพ็กเกจ `avahi-daemon`
4. **เรียกผ่าน IP โดยตรง:** ถ้าแก้ระบบเครือข่ายไม่ได้จริงๆ ให้ใช้วิธีดู IP ของ ESP32 จากหน้าจอ Serial Monitor แล้วพิมพ์เข้าตรงๆ

#### ข้อที่ 3: เหตุใดจึงต้องเรียกคำสั่ง `cJSON_Delete(root)` และ `cJSON_free(resp)` เสมอหลังจากประมวลผลเสร็จสิ้น?

**เหตุผลสำคัญ:**
1. **การทำงานของไลบรารี cJSON:** ทุกครั้งที่เราเรียกใช้คำสั่ง เช่น `cJSON_CreateObject()`, `cJSON_Parse()`, หรือเพิ่มไอเทมเข้าไปในออบเจกต์ ตัวไลบรารี cJSON จะไปสั่งจองพื้นที่หน่วยความจำในแรม (**Heap Memory**) ด้วยคำสั่ง `malloc()` เพื่อสร้างโครงสร้างข้อมูลแบบ Linked List เชื่อมต่อกันไว้
2. **คำสั่ง `cJSON_PrintUnformatted()`:** ก็จะไปสั่ง `malloc()` จองพื้นที่แรมอีกก้อนหนึ่งเพื่อนำข้อมูล JSON ทั้งหมดมาต่อเป็นข้อความสตริงยาวๆ ไว้ส่งให้ Client
3. **ถ้าไม่สั่ง Delete หรือ Free:**
   * หน่วยความจำพวกนี้จะไม่ถูกคืนกลับเข้าระบบ ทุกครั้งที่มีคนยิง Request เข้ามา แรมของบอร์ด ESP32 ก็จะถูกกินหายไปเรื่อยๆ เกิดเป็นปัญหา **Memory Leak**
   * และแรมจะแตกเป็นชิ้นเล็กชิ้นน้อย (Heap Fragmentation) จนระบบหาพื้นที่ว่างต่อเนื่องไม่ได้
   * เนื่องจาก ESP32 มีแรม Free Heap เหลือให้ใช้งานแค่ประมาณ 200 KB ถ้าปล่อยให้รั่วรอบละ 50-100 ไบต์ มีคนยิงคำขอเข้ามาไม่กี่พันครั้ง แรมก็จะเกลี้ยงบอร์ด (Out of Memory) แล้วตัวไมโครคอนโทรลเลอร์ก็จะแครชทันที (Guru Meditation Error หรือ Panic Restart)
4. **สรุปหน้าที่:**
   * `cJSON_Delete(root)` ใช้ล้างโครงสร้าง Object Tree ของ JSON ทั้งหมดคืนแรม
   * `cJSON_free((void *)resp)` ใช้คืนแรมก้อนสตริงที่สร้างขึ้นมาหลังจากส่งข้อมูล `httpd_resp_send()`
