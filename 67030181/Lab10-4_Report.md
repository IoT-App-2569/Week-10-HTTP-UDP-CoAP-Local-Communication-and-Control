### 1. สรุปสิ่งที่เราทำในแล็บนี้
ในแล็บนี้เป็นการนำระบบที่เราทำมาใน 3 แล็บแรก (HTTP ในแล็บ 10.1, UDP ในแล็บ 10.2, และ CoAP ในแล็บ 10.3) มาทดสอบประชันกันจริงๆ แบบตัวต่อตัว โดยใช้สคริปต์ Python ชื่อ `benchmark_protocols.py` ยิงคำสั่งสั่งเปิด-ปิดหลอดไฟ LED บน ESP32 ซ้ำๆ โปรโตคอลละ **50 รอบ** เพื่อเก็บค่าสถิติทางวิศวกรรม ได้แก่:
1. ความหน่วงเวลาไป-กลับ (Round-Trip Time: RTT ทั้ง Min, Mean, Max)
2. ความแกว่งของเวลา (Jitter หรือ Standard Deviation $\sigma$)
3. อัตราการสูญหายของแพ็กเก็ต (Packet Loss Rate)
4. ปริมาณการกินพื้นที่แรม Free Heap บนบอร์ด ESP32
5. สัดส่วนภาระส่วนหัวต่อข้อมูลจริง (Payload Efficiency Ratio)

### 2. บันทึกผลการทดสอบและการคำนวณ

#### 2.1 ตารางคำนวณขนาดข้อมูลตามมาตรฐาน (กิจกรรมที่ 10-4.1)

สูตรคำนวณสัดส่วนข้อมูลจริง:
$$\text{Payload Efficiency Ratio} = \frac{\text{ขนาด Payload (ไบต์)}}{\text{ขนาดข้อมูลทั้งหมดที่ส่ง (ไบต์)}} \times 100\%$$

| รายการประเมิน | HTTP REST (POST) | UDP Datagram | CoAP (PUT) |
| :--- | :---: | :---: | :---: |
| **โปรโตคอลชั้นสื่อสาร L4** | TCP | UDP | UDP |
| **ขนาด L4 Header** | 20–32 ไบต์ | **8 ไบต์** | **8 ไบต์** |
| **ขนาด L7 Application Header** | ~180–250 ไบต์ | **0 ไบต์** | **4 ไบต์** |
| **ขนาดข้อมูลคำสั่งจริง (Payload)** | 14 ไบต์ (`{"state":true}`) | 6 ไบต์ (`LED_ON`) | 1 ไบต์ (`1`) |
| **ขนาดข้อมูลรวม (L4 + L7 + Payload)** | ~214–296 ไบต์ | **14 ไบต์** | **13 ไบต์** |
| **สัดส่วนข้อมูลจริง (%)** | **~4.7 % - 6.5 %** | **~42.8 %** | **~7.7 %** |
| **ปริมาณข้อมูลเมื่อส่ง 10,000 ครั้ง** | ~2.5 - 3.0 Megabytes | ~140 Kilobytes | ~130 Kilobytes |

> **สิ่งที่สังเกตได้ชัดเจน:** ถ้าเราต้องส่งคำสั่งหมื่นครั้ง HTTP จะผลาญข้อมูลไปเกือบ 3 เมกะไบต์ ในขณะที่ CoAP และ UDP ใช้ข้อมูลแค่ร้อยกว่ากิโลไบต์เท่านั้น ประหยัดกว่ากันถึง 20 กว่าเท่า

#### 2.2 ตารางบันทึกผลการทดสอบ RTT จริง 50 รอบ (กิจกรรมที่ 10-4.2)
รันคำสั่ง: `python benchmark_protocols.py --target 192.168.1.181 --rounds 50`

| โปรโตคอล | สำเร็จ (รอบ) | Loss (%) | Min RTT (ms) | Mean RTT (ms) | Max RTT (ms) | Jitter / StdDev (ms) |
| :--- | :---: | :---: | :---: | :---: | :---: | :---: |
| **HTTP REST (`/api/led`)** | 50 / 50 | 0.0% | 42.15 ms | 56.42 ms | 114.28 ms | 12.35 ms |
| **UDP Socket (`พอร์ต 3333`)** | 50 / 50 | 0.0% | 3.82 ms | 4.68 ms | 9.45 ms | 0.98 ms |
| **CoAP PUT (`/actuator/led`)** | 50 / 50 | 0.0% | 8.35 ms | 12.93 ms | 68.42 ms | 8.85 ms |

**วิเคราะห์ผลการวัด:**
* **ความเร็วในการตอบสนอง (Mean RTT):** UDP ทำเวลาได้เร็วที่สุดเฉลี่ยเพียง **4.68 ms** เร็วกว่า CoAP (12.93 ms) เกือบ 3 เท่า และเร็วกว่า HTTP (56.42 ms) ถึง **12 เท่า**
* **ความนิ่งของเวลา (Jitter):** UDP มีค่าเบี่ยงเบนมาตรฐานต่ำสุดแค่ **0.98 ms** คือเวลานิ่งและแน่นอนมาก ส่วน HTTP มีค่า Jitter สูงถึง 12.35 ms เพราะจังหวะที่มีคิวหน่วงของ TCP ทำให้เวลาแกว่ง

#### 2.3 ตารางการใช้หน่วยความจำแรมบนบอร์ด ESP32 (กิจกรรมที่ 10-4.3)
ตรวจดูค่าแรมจาก `free_heap` ใน Serial Monitor:

| สถานะการทำงานของ ESP32 | แรมคงเหลือ (Free Heap) | แรมที่ถูกใช้ไปโดยประมาณ |
| :--- | :---: | :---: |
| **ก่อนเริ่มรันเซิร์ฟเวอร์** (ต่อ Wi-Fi เฉยๆ) | ~ 248 KB | อ้างอิง (0 KB) |
| **ตอนรัน HTTP REST Server** | ~ 216 KB | ~ 32 KB |
| **ตอนรัน UDP Socket Server** | ~ 241 KB | **~ 7 KB** |
| **ตอนรัน CoAP Server (libcoap)** | ~ 205 KB | ~ 43 KB |

**วิเคราะห์เรื่องแรม:**
* **UDP Socket กินแรมน้อยที่สุด (แค่ ~7 KB):** เพราะเป็นแค่ Socket ธรรมดาบน LwIP ไม่ต้องมีโค้ดจัดการเซสชันหรือสร้างโครงสร้างข้อมูลอะไรซับซ้อน
* **HTTP Server กินแรมปานกลาง (~32 KB):** ต้องใช้บัฟเฟอร์รับส่งข้อความ และแรมที่ cJSON จองไว้ตอนสร้างออบเจกต์
* **CoAP Server กินแรมเยอะที่สุด (~43 KB):** เพราะต้องจัดสรร Stack Size ให้ Task ถึง 8 KB และตัวไลบรารี `libcoap` ต้องจองพื้นที่เก็บ Resource Tree, ข้อมูล Session, และตารางคนติดตาม Observe

### 3. วิเคราะห์ผลและตอบคำถามเชิงวิศวกรรม

#### 1. เปรียบเทียบจุดเด่นและจุดด้อย (Pros & Cons Matrix)

* **HTTP (REST API over TCP):**
  * **ข้อดี:** ใช้งานสะดวกที่สุด ใครๆ ก็ใช้เป็น เปิดดูผ่านหน้าเว็บบราวเซอร์บนคอมหรือมือถือได้ทันที ไม่ต้องลงโปรแกรมอะไรเพิ่ม และรูปแบบ JSON ก็อ่านเข้าใจง่าย
  * **ข้อด้อย:** ช้าที่สุดและเปลืองข้อมูลที่สุด มี Header ใหญ่มาก ทำให้กินแบนด์วิดท์และเปลืองแบตเตอรี่ ไม่เหมาะกับงานที่ต้องการความเร็วสูงหรืออุปกรณ์ใช้ถ่าน
* **UDP (Raw Socket):**
  * **ข้อดี:** เร็วที่สุด ความหน่วงต่ำมาก (แค่ 4 ms) ส่งข้อมูลได้ไวสุดๆ แทบไม่มี Header (แค่ 8 ไบต์) และกินแรมน้อยที่สุดบนไมโครคอนโทรลเลอร์
  * **ข้อด้อย:** ไม่มีการรับประกันว่าข้อมูลจะถึงปลายทาง (ส่งแบบเสี่ยงดวง) ไม่มีรูปแบบข้อความมาตรฐาน ต้องเขียนโค้ดจัดการเองทั้งหมด และข้ามเราเตอร์ไม่ได้ถ้าใช้โหมด Broadcast
* **CoAP (RFC 7252 over UDP):**
  * **ข้อดี:** รวมข้อดีของทั้งสองฝั่งเข้าด้วยกัน คือ มีโครงสร้าง URL แบบ RESTful เหมือน HTTP แต่ตัวเบา วิ่งบน UDP มี Header แค่ 4 ไบต์ และมีโหมด Confirmable (CON) คอยส่งซ้ำให้ถ้าข้อมูลหลุด มีระบบค้นหาตัวเอง และรองรับ Observe
  * **ข้อด้อย:** ตัวไลบรารี `libcoap` กินแรมค่อนข้างเยอะ และเครื่องคอมพิวเตอร์ทั่วไปไม่มีเครื่องมือ CoAP ติดตั้งมาให้ ต้องลงไลบรารีอย่าง `aiocoap` เพิ่มถึงจะคุยได้

#### 2. การตัดสินใจเลือกใช้โปรโตคอลในกรณีศึกษาจริง (Engineering Case Studies)

#### กรณีศึกษาที่ 1: ระบบเซนเซอร์วัดความชื้นในดินและวาล์วน้ำเพื่อการเกษตรอัจฉริยะ (โซลาร์เซลล์ขนาดเล็ก ติดตั้งกลางแจ้งห่างไกล)
* **โปรโตคอลที่เลือก:** **CoAP (Constrained Application Protocol)**
* **เหตุผลที่เลือก:**
  1. เพราะระบบนี้ใช้แผงโซลาร์เซลล์เล็กๆ และแบตเตอรี่ สิ่งสำคัญที่สุดคือ **ต้องกินไฟน้อยที่สุด** การใช้ CoAP บน UDP ช่วยให้บอร์ดตื่นขึ้นมาส่งข้อมูลเซนเซอร์ในโหมด NON แล้วกลับไปนอนหลับลึก (Deep Sleep) ได้ในเวลาไม่กี่มิลลิวินาที ทำให้แบตอยู่ได้นานหลายเดือน
  2. ตอนสั่งเปิด-ปิดวาล์วน้ำ เราสามารถเลือกใช้โหมด **Confirmable (CON)** ได้ เพื่อให้มั่นใจได้ 100% ว่าคำสั่งส่งถึงวาล์วน้ำจริง ถ้าส่งไม่ผ่านตัว CoAP จะส่งซ้ำให้อัตโนมัติ วาล์วน้ำไม่เปิดค้างแน่นอน
  3. Header มีขนาดเล็กแค่ 4 ไบต์ ประหยัดค่าเน็ตซิมเซลลูลาร์ (NB-IoT/4G) ได้เยอะมากครับ

#### กรณีศึกษาที่ 2: เว็บแดชบอร์ดสำหรับฝ่ายซ่อมบำรุงในโรงงาน (เปิดดูสถานะและตั้งค่าผ่านเว็บบราวเซอร์บนแท็บเล็ต/สมาร์ตโฟน)
* **โปรโตคอลที่เลือก:** **HTTP RESTful API (ร่วมกับ mDNS)**
* **เหตุผลที่เลือก:**
  1. เพราะโจทย์บอกชัดเจนว่าต้องการให้ **เปิดดูผ่านเว็บบราวเซอร์บนมือถือหรือแท็บเล็ตได้** ซึ่ง HTTP เป็นโปรโตคอลมาตรฐานที่เบราว์เซอร์ทุกตัว (Chrome, Safari) รองรับอยู่แล้ว ช่างซ่อมบำรุงแค่พิมพ์ชื่อ `http://esp32-node.local` ก็เปิดหน้าเว็บตั้งค่าได้ทันที ไม่ต้องลงแอปอะไรเพิ่ม
  2. การตั้งค่าพารามิเตอร์ของเครื่องจักร เหมาะกับการส่งเป็นข้อความ JSON ผ่าน HTTP POST เพราะอ่านง่าย ตรวจสอบความถูกต้องได้ชัดเจน มีรหัสสถานะบอกว่าบันทึกสำเร็จหรือไม่ (`200 OK`)
  3. เครื่องจักรในโรงงานมีไฟฟ้าเลี้ยงตลอดเวลาอยู่แล้ว ไม่ต้องกังวลเรื่องแบตเตอรี่ การเลือก HTTP จึงสะดวกและคุ้มค่าที่สุดในแง่การใช้งานครับ

#### กรณีศึกษาที่ 3: ระบบควบคุมแขนกลอุตสาหกรรมความเร็วสูง (ส่งพิกัด X, Y, Z ด้วยความถี่ 100 Hz ใน LAN ปิด)
* **โปรโตคอลที่เลือก:** **UDP Raw Datagram (Unicast)**
* **เหตุผลที่เลือก:**
  1. เพราะความถี่ 100 Hz หมายความว่าเราต้องส่งข้อมูลใหม่ **ทุกๆ 10 มิลลิวินาที** มีแค่ UDP เท่านั้นที่ทำความเร็วได้ทัน (RTT ของ UDP เฉลี่ยแค่ ~4 ms)
  2. **ไม่มีปัญหาคิวติดขัด (No Head-of-Line Blocking):** ถ้าเราไปใช้ TCP แล้วมีข้อมูลพิกัดชุดใดชุดหนึ่งหล่นหาย ตัว TCP จะสั่งหยุดรอและส่งซ้ำ ซึ่งจะทำให้แขนกลกระตุกอย่างรุนแรง แต่ถ้าเป็น UDP ถ้าพิกัดเก่าหายไป เราก็ไม่ต้องสนใจ เพราะอีก 10 มิลลิวินาทีข้างหน้าพิกัดชุดใหม่ล่าสุดก็ส่งมาถึงแล้ว แขนกลจะเคลื่อนที่ได้อย่างนุ่มนวล
  3. ในเครือข่ายแลนปิด สัญญาณรบกวนมีน้อยมาก อัตราข้อมูลสูญหายแทบจะเป็นศูนย์ UDP จึงปลอดภัยและตอบโจทย์ความเร็วสูงสุด
