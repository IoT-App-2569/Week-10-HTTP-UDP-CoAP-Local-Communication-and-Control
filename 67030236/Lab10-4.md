## 4. วิเคราะห์ผลและสรุปบทเรียนเชิงวิศวกรรม (Engineering Synthesis)

ให้นักศึกษาตอบคำถามเชิงวิเคราะห์ต่อไปนี้ลงในรายงานการทดลอง

### 1. เปรียบเทียบจุดเด่นและจุดด้อย (Pros & Cons Matrix)
จงสรุปข้อดีและข้อจำกัดของ **HTTP, UDP, และ CoAP** จากผลการทดลองจริง 
* **HTTP** ข้อดี: เข้ากันได้กับโครงสร้างเว็บและเว็บบราวเซอร์โดยตรง มีความน่าเชื่อถือสูงบนสแตก TCP และรองรับรูปแบบข้อมูลที่เป็นมาตรฐานสากล เช่น JSON
ข้อจำกัด: มี Protocol Overhead สูงมาก (~190–300 ไบต์ต่อคำขอ) ใช้เวลา RTT นานที่สุด และกินทรัพยากรประมวลผลมาก ไม่เหมาะกับอุปกรณ์ข้อจำกัดสูง
* **UDP** ข้อดี: ส่งข้อมูลได้เร็วที่สุด ความหน่วงเวลา (Latency) และ Jitter ต่ำสุด กินแรมและ Overhead น้อยที่สุด (~14 ไบต์ต่อคำขอ) ประสิทธิภาพ Payload สูงถึง ~42.8%
ข้อจำกัด: เป็นการส่งแบบไร้สถานะ (Connectionless) ไม่มีการรับประกันการส่งถึงปลายทาง (No ACK/Retransmission) ข้อมูลอาจสูญหายหรือสลับลำดับได้
* **CoAP** ข้อดี: ออกแบบมาเพื่อ IoT โดยเฉพาะ มีโครงสร้างแบบ RESTful (GET/PUT/POST) บน UDP ส่วนหัวเล็กกะทัดรัด (ไบนารีเพียง 4–8 ไบต์) และเลือกระดับความน่าเชื่อถือได้ (CON/NON)
ข้อจำกัด: ไลบรารี (libcoap) มีความซับซ้อนและใช้พื้นที่ RAM สูงที่สุด (~35–50 KB) สำหรับจัดการ State Machine/Resource Tree และต้องใช้ Proxy หากต้องการต่อเข้ากับเว็บบราวเซอร์ทั่วไป

### 2. กรณีศึกษาการตัดสินใจเลือกใช้โปรโตคอล (Engineering Case Studies)
หากท่านเป็นหัวหน้าวิศวกรออกแบบระบบ IoT จงเลือกโปรโตคอลที่เหมาะสมที่สุดสำหรับแต่ละกรณีศึกษาต่อไปนี้ พร้อมให้เหตุผลทางวิศวกรรมสนับสนุน

* **กรณีศึกษาที่ 1** *ระบบเซนเซอร์วัดความชื้นในดินและวาล์วน้ำเพื่อการเกษตรอัจฉริยะ ทำงานด้วยแบตเตอรี่โซลาร์เซลล์ขนาดเล็ก ติดตั้งกลางแจ้งห่างไกล*
  * **โปรโตคอลที่เลือก** CoAP
  * **เหตุผลทางวิศวกรรม** อุปกรณ์ทำงานด้วยพลังงานจำกัด จึงต้องการโปรโตคอลที่มี Overhead ต่ำเพื่อลดเวลาเปิดใช้งานตัวส่งสัญญาณวิทยุ (ประหยัดพลังงาน) โดย CoAPมีขนาดแพ็กเก็ตเล็กมากบน UDP แต่ยังคงความน่าเชื่อถือผ่านโหมด Confirmable (CON) ที่มีการส่งซ้ำ (Retransmission) อัตโนมัติเมื่อสัญญาณกลางแจ้งขาดหาย พร้อมทั้งมีรูปแบบ URI ที่จัดการค่าพารามิเตอร์ของเซนเซอร์และวาล์วได้อย่างเป็นระบบ

* **กรณีศึกษาที่ 2** *เว็บแดชบอร์ดสำหรับฝ่ายซ่อมบำรุงในโรงงาน เพื่อเปิดดูสถานะและตั้งค่าพารามิเตอร์ของอุปกรณ์ผ่านเว็บบราวเซอร์บนแท็บเล็ต/สมาร์ตโฟน*
  * **โปรโตคอลที่เลือก** HTTP REST
  * **เหตุผลทางวิศวกรรม** เว็บบราวเซอร์มาตรฐานบนสมาร์ตโฟนและแท็บเล็ตรองรับโพรโทคอล HTTP และ JSON โดยกำเนิด (Native Web Compatibility) สามารถเชื่อมต่อและดึงข้อมูลมาแสดงผลบน Dashboard ได้ทันทีโดยไม่ต้องติดตั้งซอฟต์แวร์เสริมหรือใช้ CoAP-HTTP Proxy ตัวระบบไม่ได้จำกัดพลังงานและอยู่ในเครือข่ายที่มีแบนด์วิดท์เพียงพอ ความสะดวกในการพัฒนาและการบำรุงรักษาจึงมีความสำคัญสูงสุด

* **กรณีศึกษาที่ 3** *ระบบควบคุมแขนกลอุตสาหกรรมความเร็วสูง ที่ต้องการส่งพิกัดตำแหน่งแกนหมุน (X, Y, Z) ด้วยความถี่ 100 ครั้งต่อวินาที (100 Hz) ภายในเครือข่าย LAN ปิด (intranet)*
  * **โปรโตคอลที่เลือก** UDP Socket
  * **เหตุผลทางวิศวกรรม** ที่ความถี่ 100 Hz ระบบต้องการความหน่วงเวลาต่ำที่สุด (Ultra-low Latency) และต้องการส่งข้อมูลพิกัดล่าสุดอย่างต่อเนื่อง การทำงานบนเครือข่าย LAN แบบปิดมีความเสี่ยงต่อ Packet Loss ต่ำอยู่แล้ว การตัดกระบวนการ TCP Handshake และลดภาระ Application Header ให้เหลือ 0 ไบต์ ทำให้มี Throughput สูงสุด และไม่มีปัญหาความล่าช้าจากการรอส่งซ้ำแพ็กเก็ตเก่า (Head-of-Line Blocking) ซึ่งไม่จำเป็นสำหรับข้อมูลพิกัดแบบ Real-time streaming
