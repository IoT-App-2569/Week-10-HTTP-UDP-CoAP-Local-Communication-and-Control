1. นำผลการ Query `/.well-known/core` มาแสดงในรายงาน พร้อมอธิบายรูปแบบ **CoRE Link Format (RFC 6690)** ว่าแสดงข้อมูลทรัพยากรอย่างไร
```
การอธิบายรูปแบบ CoRE Link Format (RFC 6690):
ข้อมูลทรัพยากร (Resources) จะถูกครอบด้วยเครื่องหมาย < > เพื่อระบุตำแหน่งของ URI Path
แต่ละทรัพยากรจะถูกคั่นด้วยเครื่องหมายจุลภาค (,)
จากผลลัพธ์แสดงว่าโหนดมี 2 ทรัพยากรพร้อมให้บริการ คือ:
</sensor/pot>: ทรัพยากรสำหรับอ่านค่าเซนเซอร์อนาล็อก
</actuator/led>: ทรัพยากรสำหรับควบคุมสถานะหลอดไฟ LED
```

2. อธิบายความแตกต่างของแพ็กเก็ต CoAP ระหว่าง **CON (Confirmable)** และ **NON (Non-confirmable)** เมื่อทดสอบในเครือข่ายที่มีการรบกวนสัญญาณ
```
CON (Confirmable): เป็นการส่งแบบต้องมีการยืนยัน ปลายทางต้องตอบกลับด้วยแพ็กเก็ต ACK หากเกิดสัญญาณรบกวนจนแพ็กเก็ตสูญหาย ตัวส่งจะจับเวลา (Timeout) และส่งซ้ำให้อัตโนมัติ (Retransmission) ข้อมูลจึงมีความถูกต้องแม่นยำสูง
NON (Non-confirmable): เป็นการส่งแบบไม่ต้องยืนยัน (Fire-and-forget) ปลายทางไม่ต้องส่ง ACK กลับ หากมีสัญญาณรบกวนจนข้อมูลตกหล่น จะไม่มีการส่งซ้ำและข้อมูลจะสูญหายทันที เหมาะกับข้อมูลที่ส่งต่อเนื่องเป็นประจำ เช่น ค่าอุณหภูมิหรือสตรีมมิ่งเซนเซอร์
```

3. ทำไม CoAP จึงเหมาะสมกับโปรโตคอลการสื่อสารบนเครือข่ายเช่น Thread, Zigbee IP หรือ NB-IoT มากกว่า HTTP?
```
ขนาดแพ็กเก็ตเล็กมาก (Low Overhead): Header ของ CoAP มีขนาดคงที่เริ่มต้นเพียง 4 ไบต์ ในรูปแบบไบนารี (Binary) ขณะที่ HTTP เป็นข้อความตัวอักษร (Text-based) ซึ่งส่วนหัวกินพื้นที่หลายสิบถึงหลายร้อยไบต์
ทำงานบน UDP: ไม่ต้องเสียเวลาทำ TCP 3-Way Handshake ทำให้ประหยัดแบนด์วิดท์ ส่งข้อมูลได้เร็ว และประหยัดพลังงานแบตเตอรี่ของอุปกรณ์ขนาดเล็ก
เหมาะกับข้อจำกัดของเครือข่าย: เครือข่าย LPWAN อย่าง NB-IoT หรือ 6LoWPAN (บน Thread/Zigbee) มีขนาด MTU ต่อเฟรมจำกัด แพ็กเก็ตที่เล็กของ CoAP จึงส่งได้จบในรอบเดียวโดยไม่ต้องตัดแบ่งเฟรม (Fragmentation)
```
