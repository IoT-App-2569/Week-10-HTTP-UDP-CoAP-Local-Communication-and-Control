## คำถามท้ายการทดลอง
1. นำผลการวัดค่า RTT Latency ของ UDP ในกิจกรรมที่ 10-2.5 มาเปรียบเทียบกับความหน่วงเวลาของ HTTP RESTful ในใบงาน 10.1 และวิเคราะห์ความแตกต่าง
```
ผลการเปรียบเทียบ: UDP มีความหน่วงเวลา (Latency) ต่ำกว่า HTTP RESTful อย่างเห็นได้ชัด (UDP ตอบสนองในระดับไม่กี่มิลลิวินาที ขณะที่ HTTP มักใช้เวลา 20–50+ ms)

การวิเคราะห์ความแตกต่าง:

UDP (Connectionless): ส่งข้อมูลออกไปทันทีแบบ Fire-and-forget โดยไม่มีขั้นตอนสร้างการเชื่อมต่อ (No Handshake) และไม่มีการส่งสัญญาณยืนยัน (ACK) จึงมีความหน่วงต่ำมาก

HTTP (Connection-oriented / TCP): ต้องผ่านกระบวนการ TCP 3-Way Handshake, มีภาระข้อมูลส่วนหัว (HTTP Header Overhead) ขนาดใหญ่ และมีกลไกยืนยันการรับส่งข้อมูล ทำให้เกิดความหน่วงสะสมสูงกว่า
```

2. รันสคริปต์ `udp_listener.py` เป็นเวลา 1 นาที จงบันทึกค่าและคำนวณอัตราการสูญหายของแพ็กเก็ต (Packet Loss Rate) พร้อมวิเคราะห์สาเหตุที่ทำให้เกิดการสูญหายบนเครือข่าย Wi-Fi
```
ผลการบันทึก (1 นาที):แพ็กเก็ตที่ส่งทั้งหมด (Total Sent): 600 แพ็กเก็ต (อิงตามอัตราส่ง 100 ms/ครั้ง หรือ 10 Hz)แพ็กเก็ตที่สูญหาย (Total Lost): 0 แพ็กเก็ต (จากข้อมูล Seq: 4144 ถึง 4152 รันต่อเนื่องไม่มีตกหล่น)สูตรคำนวณ: $\text{Packet Loss Rate} = \left(\frac{\text{Total Lost}}{\text{Total Sent}}\right) \times 100 = \left(\frac{0}{600}\right) \times 100 = \mathbf{0\%}$การวิเคราะห์สาเหตุการสูญหายบน Wi-Fi:เกิดจากการรบกวนของคลื่นความถี่วิทยุ (RF Interference), ความแออัดของช่องสัญญาณ (Channel Congestion), สัญญาณ Wi-Fi อ่อนลงตามระยะห่าง หรือบัฟเฟอร์ของสแตกเครือข่ายเต็ม โดยที่โพรโทคอล UDP ไม่มีการตรวจสอบความถูกต้องและไม่มีการส่งซ้ำ (No Retransmission)
```

3. อธิบายข้อดีและข้อจำกัดของการใช้ `255.255.255.255` (UDP Broadcast) ในระบบ IoT และในสถานการณ์ใดที่ควรเปลี่ยนไปใช้ **UDP Multicast** หรือ **Unicast** แทน?
```
ข้อดี: อุปกรณ์ส่งข้อมูลครั้งเดียว กระจายให้ทุกเครื่องใน Local Subnet ได้พร้อมกันโดยผู้ส่งไม่ต้องรู้หมายเลข IP ของผู้รับ
ข้อจำกัด: สร้างขยะบนเครือข่าย (Broadcast Storm) รบกวนอุปกรณ์อื่นที่ไม่เกี่ยวข้อง และแพ็กเก็ตไม่สามารถข้าม Router ไปยัง Subnet อื่นได้

สถานการณ์ที่ควรเปลี่ยนไปใช้รูปแบบอื่น:

เปลี่ยนไปใช้ UDP Multicast: เมื่อต้องการส่งข้อมูลกลุ่มแบบ One-to-Many เฉพาะอุปกรณ์ที่ลงทะเบียนรับฟัง (เช่น ระบบ Smart Home หลายตัว) โดยไม่รบกวนเครื่องอื่น และต้องการส่งข้าม Subnet

เปลี่ยนไปใช้ Unicast: เมื่อต้องการส่งข้อมูลแบบ Point-to-Point เจาะจงไปยังเซิร์ฟเวอร์หรืออุปกรณ์ตัวเดียว เช่น การอัปโหลดข้อมูลเทเลเมทรีขึ้น Gateway กลาง เพื่อประหยัดแบนด์วิดท์เครือข่าย
```
