# Week 10: ผลที่คาดว่าจะได้ (Lab 10.1 - 10.4)

> **สถานะ: ผลที่คาดว่าจะได้ ยังไม่ได้ทดสอบบนบอร์ดจริง**
> ทุกค่าเป็นการคาดการณ์จากโค้ดและใบงาน ต้องแฟลชลงบอร์ดแล้วนำค่าจริงมาแทน

## ก่อนแฟลช

- แก้ `CONFIG_WIFI_SSID` และ `CONFIG_WIFI_PASS` ในไฟล์ `.c` ของ Lab 10.1, 10.2, 10.3
- แก้ `ESP32_IP` ใน `udp_controller.py` และ `test_coap.py` ให้ตรงกับ IP ที่บอร์ดได้รับ

## Lab 10.1: mDNS & HTTP REST

- `GET /api/status` ตอบ HTTP 200 พร้อม JSON สถานะของบอร์ด รวมถึง `free_heap`
- `POST /api/led` เปิดหรือปิด LED แล้วตอบ JSON ยืนยันสถานะ
- เข้าผ่านชื่อ mDNS (`.local`) ได้เมื่อเครื่องรองรับ mDNS
- `curl -i` แสดง Header ประมาณ 100 - 200 ไบต์ ซึ่งมากกว่า JSON ขนาดสั้น ต้องนับค่าจริงจากผลรัน

## Lab 10.2: UDP Telemetry

- บอร์ด Broadcast ข้อมูลที่พอร์ต 3334 ประมาณ 10 ครั้งต่อวินาที และรับคำสั่งที่พอร์ต 3333
- `udp_listener.py` รันครบ 1 นาทีควรได้ประมาณ 600 แพ็กเก็ต Packet Loss คาดว่าต่ำกว่า 5% บนเครือข่ายที่สัญญาณดี
- RTT ควรต่ำกว่า HTTP เพราะไม่มี TCP Handshake

## Lab 10.3: CoAP Server

| การทดสอบ | ผลที่คาดว่าจะได้ |
| :--- | :--- |
| `GET /.well-known/core` | รายการในรูปแบบ CoRE Link Format มี `/sensor/pot` และ `/actuator/led` |
| `GET /sensor/pot` | Code 2.05 Content พร้อมค่าเซนเซอร์ |
| `PUT /actuator/led` | Code 2.04 Changed และ LED เปลี่ยนสถานะ |

## Lab 10.4: Protocol Benchmark

ค่าประมาณอยู่ในตารางของใบงานแล้ว โดยกำกับว่าเป็นค่าคาดการณ์ ส่วน CoAP อ้างอิงตัวอย่าง Log ในใบงาน ส่วน HTTP และ UDP ประมาณจากลักษณะของโปรโตคอล

ลำดับที่ควรเห็น: UDP เร็วที่สุด, CoAP ใกล้เคียง UDP และ HTTP ช้าที่สุด ส่วนการใช้แรมเรียงจาก UDP น้อยที่สุด ตามด้วย HTTP และ CoAP ตามตารางในใบงาน
