## 2. เปรียบเทียบจุดเด่นและจุดด้อย

| โปรโตคอล | จุดเด่น | ข้อจำกัด |
| :--- | :--- | :--- |
| HTTP | ใช้งานง่าย รองรับ Web Browser และระบบองค์กร มีรูปแบบ Request/Response ชัดเจน | Header และ TCP มี Overhead สูง ใช้พลังงานและแบนด์วิดท์มากกว่า |
| UDP | Header เล็ก ความหน่วงต่ำ เหมาะกับ Telemetry และการส่งข้อมูลถี่ | ไม่รับประกันการส่งถึง ลำดับ หรือการส่งซ้ำ ต้องสร้างกลไกความน่าเชื่อถือเอง |
| CoAP | เบากว่า HTTP ใช้ UDP แต่ยังมีรูปแบบ RESTful รองรับ CON/NON และ Observe | ต้องใช้ CoAP Client/Proxy เฉพาะ ไม่เหมาะกับ Web Browser โดยตรง และต้องจัดการความน่าเชื่อถือให้เหมาะสม |

## 3. กรณีศึกษาการเลือกโปรโตคอล

### กรณีศึกษาที่ 1: ระบบเกษตรอัจฉริยะพลังงานต่ำ

**โปรโตคอลที่เลือก:** CoAP

**เหตุผลทางวิศวกรรม:** อุปกรณ์ทำงานด้วยแบตเตอรี่และอยู่ห่างไกล จึงต้องลดขนาดแพ็กเก็ตและเวลาที่วิทยุทำงาน CoAP ใช้ UDP และมี Header เล็กกว่า HTTP รองรับ CON สำหรับคำสั่งเปิดวาล์วที่ต้องการความถูกต้อง และใช้ NON/Observe สำหรับข้อมูลเซนเซอร์ที่ส่งเป็นระยะได้ หากเครือข่ายเป็น Cellular โดยตรง อาจใช้ CoAP ผ่าน DTLS/เครือข่ายที่รองรับแทน HTTP

### กรณีศึกษาที่ 2: Web Dashboard สำหรับฝ่ายซ่อมบำรุง

**โปรโตคอลที่เลือก:** HTTP REST

**เหตุผลทางวิศวกรรม:** ผู้ใช้เข้าถึงผ่าน Web Browser บนแท็บเล็ตหรือสมาร์ตโฟน ซึ่งรองรับ HTTP โดยตรง มีเครื่องมือพัฒนาและระบบรักษาความปลอดภัยพร้อมใช้งาน สามารถใช้ HTTPS เพื่อเข้ารหัสข้อมูลและยืนยันตัวตนได้ แม้มี Overhead สูงกว่า แต่เหมาะกับการอ่านสถานะและตั้งค่าที่ไม่ได้ต้องการความถี่สูงมาก

### กรณีศึกษาที่ 3: ควบคุมแขนกล 100 Hz บน LAN ปิด

**โปรโตคอลที่เลือก:** UDP Unicast

**เหตุผลทางวิศวกรรม:** ต้องส่งข้อมูลตำแหน่งด้วยความถี่สูงและต้องการความหน่วงต่ำใน LAN ที่ควบคุมได้ UDP ไม่มี TCP Handshake และมี Header เล็ก เหมาะกับการส่งข้อมูลแบบต่อเนื่อง อย่างไรก็ตามระบบจริงควรเพิ่ม Sequence Number, Timestamp, Watchdog และกลไกตรวจสอบความปลอดภัย เพราะ UDP ไม่รับประกันการส่งถึง และการควบคุมแขนกลไม่ควรพึ่งพา UDP เพียงอย่างเดียวโดยไม่มีระบบหยุดฉุกเฉินหรือ Fail-safe
