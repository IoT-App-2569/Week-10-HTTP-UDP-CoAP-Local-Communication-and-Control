# รายงานผลการทดลอง: ใบงานที่ 10.4

**เรื่อง:** การทดสอบเปรียบเทียบสมรรถนะของโปรโตคอลเครือข่าย

## ข้อมูลระบบที่ใช้เปรียบเทียบ

การเปรียบเทียบอ้างอิงจากโปรเจกต์ที่จัดทำในแลป 1–3 และใช้ ESP32 เครื่องเดียวกัน:

| รายการ | ค่า |
| :--- | :--- |
| IP Address ของ ESP32 | `10.14.195.186` |
| HTTP REST Server | TCP port `80` |
| UDP Control Server | UDP port `3333` |
| CoAP Server | UDP port `5683` |
| LED | GPIO 2 |
| Potentiometer | GPIO 34 / ADC1 Channel 6 |

## 1. การวิเคราะห์ขนาดข้อมูลและ Protocol Overhead

คำสั่งควบคุม LED ในแต่ละโปรโตคอลใช้ข้อมูลต่างกัน:

- HTTP REST: `{"state":true}` มี Payload 14 ไบต์
- UDP Socket: `LED_ON` มี Payload 6 ไบต์
- CoAP: `1` มี Payload 1 ไบต์

| รายการประเมิน | HTTP REST (POST) | UDP Datagram | CoAP (PUT) |
| :--- | :---: | :---: | :---: |
| Transport Layer | TCP | UDP | UDP |
| L4 Header | ประมาณ 20–32 ไบต์ | 8 ไบต์ | 8 ไบต์ |
| L7/Application Header | ประมาณ 180–250 ไบต์ | 0 ไบต์ | ประมาณ 4 ไบต์ |
| Payload | 14 ไบต์ | 6 ไบต์ | 1 ไบต์ |
| ข้อมูลรวมโดยประมาณ | 214–296 ไบต์ | 14 ไบต์ | 13 ไบต์ |
| Payload Efficiency | ประมาณ 4.7–6.5% | ประมาณ 42.8% | ประมาณ 7.6% |

คำนวณด้วยสูตร:

```text
Payload Efficiency Ratio =
    Payload Size / Total Transmitted Bytes × 100
```

เมื่อส่งคำสั่ง 10,000 ครั้ง UDP และ CoAP จะใช้ข้อมูลน้อยกว่า HTTP อย่างมาก เนื่องจากไม่มี HTTP Header ขนาดใหญ่ และ CoAP ใช้ Binary Header ขนาดเล็กบน UDP

## 2. ผลการวัด RTT และ Packet Loss

### 2.1 HTTP REST

จากผลที่บันทึกไว้ในแลป 1 การเรียก API ควบคุม LED ผ่าน `POST /api/led` มีค่าที่ใช้เปรียบเทียบดังนี้:

| โปรโตคอล | จำนวนรอบ | Min RTT | Mean RTT | Max RTT |
| :--- | :---: | ---: | ---: | ---: |
| HTTP REST | 50 รอบ | 24.80 ms | 44.60 ms | 182.30 ms |

HTTP มีความหน่วงสูงกว่าเนื่องจากใช้ TCP และมี HTTP Request/Response Header เพิ่มจากข้อมูลคำสั่งจริง

### 2.2 UDP Socket

จากแลป 2 มีการส่งคำสั่ง `LED_ON` และ `LED_OFF` สลับกัน 10 รอบไปยัง `10.14.195.186:3333`:

| โปรโตคอล | จำนวนรอบ | Min RTT | Mean RTT | Max RTT |
| :--- | :---: | ---: | ---: | ---: |
| UDP Socket | 10 รอบ | 5.41 ms | 8.96 ms | 23.70 ms |

สำหรับ Telemetry Broadcast ที่พอร์ต `3334` ทดสอบเป็นเวลา 1 นาที:

| รายการ | ค่า |
| :--- | ---: |
| Received | 596 packets |
| Lost | 4 packets |
| Packets ที่ควรได้รับ | 600 packets |
| Packet Loss Rate | 0.67% |

```text
Packet Loss Rate = 4 / (596 + 4) × 100 = 0.67%
```

### 2.3 CoAP

จากแลป 3 การทดสอบ CoAP ไปยัง `10.14.195.186:5683` ได้ผลดังนี้:

| การทดสอบ | ผลลัพธ์ |
| :--- | :--- |
| GET `/.well-known/core` | พบ `/sensor/pot` และ `/actuator/led` |
| GET `/sensor/pot` | ได้ค่า Potentiometer `2385`, Response `2.05 Content` |
| PUT `/actuator/led` ด้วย `1` | LED ติด, Response `2.04 Changed` |
| PUT `/actuator/led` ด้วย `0` | LED ดับ, Response `2.04 Changed` |

ยังไม่มีการบันทึกผลการวัด CoAP แบบ Benchmark 50 รอบ จึงไม่กำหนดค่า Min, Mean, Max, Jitter หรือ Packet Loss ขึ้นเองแทนผลจริง

### 2.4 ตารางสรุปผลที่มีจากแลปก่อนหน้า

| โปรโตคอล | รอบที่วัด | Packet Loss | Min RTT (ms) | Mean RTT (ms) | Max RTT (ms) | Jitter |
| :--- | :---: | :---: | ---: | ---: | ---: | :---: |
| HTTP REST | 50 | 0% | 24.80 | 44.60 | 182.30 | ไม่ได้บันทึก |
| UDP Socket | 10 | 0% ในชุดคำสั่ง | 5.41 | 8.96 | 23.70 | ไม่ได้บันทึก |
| CoAP | การทดสอบ Resource/คำสั่ง | ไม่ได้วัด | ไม่ได้วัด | ไม่ได้วัด | ไม่ได้วัด | ไม่ได้วัด |

ค่า Packet Loss `0.67%` ของ UDP เป็นผลจาก Telemetry Broadcast แยกจากชุดวัด RTT คำสั่งควบคุม

## 3. การเปรียบเทียบจุดเด่นและจุดด้อย

| โปรโตคอล | จุดเด่น | ข้อจำกัด |
| :--- | :--- | :--- |
| HTTP REST | ใช้งานง่าย มีรูปแบบ Request/Response ชัดเจน รองรับ Web Browser และระบบองค์กร | TCP และ Header มี Overhead สูง ทำให้ RTT และการใช้แบนด์วิดท์สูงกว่า |
| UDP | Header เล็ก RTT ต่ำ เหมาะกับคำสั่งที่ส่งถี่และ Telemetry แบบ Real-time | ไม่รับประกันลำดับ การส่งถึง หรือการส่งซ้ำ ต้องสร้าง ACK และตรวจ Sequence Number เอง |
| CoAP | ใช้ UDP แต่ยังมีรูปแบบ RESTful, Header เล็ก, รองรับ CON/NON และ Resource Discovery | ต้องใช้ Client ที่รองรับ CoAP ไม่สามารถเรียกจาก Web Browser ได้โดยตรง และต้องเลือกกลไกความน่าเชื่อถือให้เหมาะสม |

จากข้อมูลที่มี UDP ให้ RTT เฉลี่ยต่ำที่สุด ส่วน HTTP ให้โครงสร้างการใช้งานที่ง่ายที่สุด ขณะที่ CoAP อยู่ระหว่างความเบาของ UDP และรูปแบบ Resource แบบ RESTful

## 4. การวิเคราะห์ RAM Footprint

แลป 1 บันทึกค่า Free Heap ของ ESP32 ขณะให้บริการ HTTP REST ไว้ที่ `217808 bytes` จากผล `GET /api/status`

| โปรโตคอล | Free Heap ที่บันทึกได้ |
| :--- | ---: |
| HTTP REST | 217808 bytes |
| UDP Socket | ยังไม่ได้บันทึก |
| CoAP | ยังไม่ได้บันทึก |

จึงยังไม่สรุปว่าโปรโตคอลใดใช้ RAM น้อยที่สุดจากข้อมูล Heap เพราะต้องวัดด้วยวิธีเดียวกัน ขณะบอร์ดรันเฟิร์มแวร์แต่ละแบบและอยู่ในสภาวะเดียวกัน

## 5. กรณีศึกษาการเลือกโปรโตคอล

### กรณีศึกษาที่ 1: ระบบเกษตรอัจฉริยะพลังงานต่ำ

**โปรโตคอลที่เลือก:** CoAP

**เหตุผลทางวิศวกรรม:** อุปกรณ์ใช้แบตเตอรี่และอยู่ห่างไกล จึงควรลดขนาดแพ็กเก็ตและเวลาที่วิทยุทำงาน CoAP ใช้ UDP และมี Header เล็กกว่า HTTP รองรับ CON สำหรับคำสั่งเปิดวาล์วที่ต้องการความถูกต้อง และสามารถใช้ NON หรือ Observe กับข้อมูลเซนเซอร์ที่ยอมให้สูญหายบางส่วนได้ หากใช้เครือข่าย Cellular ควรพิจารณา DTLS และการจัดการพลังงานเพิ่มเติม

### กรณีศึกษาที่ 2: Web Dashboard สำหรับฝ่ายซ่อมบำรุง

**โปรโตคอลที่เลือก:** HTTP REST

**เหตุผลทางวิศวกรรม:** Web Browser บนแท็บเล็ตและสมาร์ตโฟนรองรับ HTTP โดยตรง ไม่ต้องติดตั้ง CoAP Client เพิ่ม มีเครื่องมือพัฒนาและระบบรักษาความปลอดภัยพร้อมใช้งาน และสามารถใช้ HTTPS เพื่อเข้ารหัสข้อมูลและยืนยันตัวตนได้ แม้ HTTP จะมี Overhead สูงกว่า แต่เหมาะกับการดูสถานะและตั้งค่าที่ไม่ได้ต้องการความถี่ระดับ Real-time สูง

### กรณีศึกษาที่ 3: ระบบควบคุมแขนกล 100 Hz บน LAN ปิด

**โปรโตคอลที่เลือก:** UDP Unicast

**เหตุผลทางวิศวกรรม:** ระบบต้องส่งพิกัด X, Y, Z ด้วยความถี่สูงและต้องการ RTT ต่ำใน LAN ที่ควบคุมได้ UDP ไม่มี TCP Handshake และมี Header ขนาดเล็ก ข้อมูลตำแหน่งล่าสุดสามารถแทนข้อมูลเก่าได้ทันทีโดยไม่ต้องรอการส่งซ้ำ อย่างไรก็ตามระบบจริงควรเพิ่ม Sequence Number, Timestamp, Watchdog, ตรวจสอบขอบเขตคำสั่ง และระบบหยุดฉุกเฉิน เนื่องจาก UDP ไม่รับประกันการส่งถึงและไม่ควรใช้เป็นกลไกความปลอดภัยเพียงอย่างเดียว

## 6. สรุปผลการทดลอง

จากข้อมูลของแลปก่อนหน้า HTTP REST มี Mean RTT `44.60 ms` ขณะที่ UDP Socket มี Mean RTT `8.96 ms` จึงเหมาะกับงานที่ต้องการการตอบสนองรวดเร็วกว่า ส่วน CoAP มีโครงสร้าง Resource แบบ RESTful และลด Overhead ด้วยการทำงานบน UDP เหมาะกับอุปกรณ์ IoT ที่มีข้อจำกัดด้านพลังงานและแบนด์วิดท์

การเลือกโปรโตคอลควรพิจารณาร่วมกันทั้งความหน่วง ความน่าเชื่อถือ ขนาดข้อมูล ความเข้ากันได้กับ Client และข้อจำกัดของอุปกรณ์ ไม่ควรเลือกจากค่า RTT เพียงอย่างเดียว
