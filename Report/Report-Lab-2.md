# รายงานผลการทดลอง: ใบงานที่ 10.2

**เรื่อง:** การสื่อสารความหน่วงต่ำด้วย UDP Socket และการถ่ายทอดข้อมูล Real-time Telemetry

## 1. บันทึกผลการทดลอง

### 1.1 ผลการวัด RTT

การทดสอบใช้ UDP Control Server ที่พอร์ต `3333` โดยส่งคำสั่งสลับ `LED_ON` และ `LED_OFF` รวม 10 รอบไปยัง ESP32

| รายการ | ผลการทดลอง |
| :--- | :--- |
| IP Address ของ ESP32 | `10.14.195.186` |
| UDP Control Port | `3333` |
| จำนวนรอบ | 10 รอบ |
| Average RTT | 8.96 ms |
| Minimum RTT | 5.41 ms |
| Maximum RTT | 23.70 ms |

**ผลจาก `udp_controller.py`:**

```text
Sending control commands to 10.14.195.186:3333...
Round 01: Sent 'LED_ON' -> Reply 'ACK:LED_ON' | RTT: 11.84 ms
Round 02: Sent 'LED_OFF' -> Reply 'ACK:LED_OFF' | RTT: 7.92 ms
...
Round 10: Sent 'LED_OFF' -> Reply 'ACK:LED_OFF' | RTT: 8.37 ms

Average UDP RTT Latency: 8.96 ms (Min: 5.41 ms, Max: 23.70 ms)
```

### 1.2 ผลการรับ Telemetry และ Packet Loss

ESP32 ส่งข้อมูล Potentiometer แบบ UDP Broadcast ไปยัง `255.255.255.255` พอร์ต `3334` ทุก 100 ms หรือ 10 Hz และใช้ Sequence Number ตรวจสอบแพ็กเก็ตที่สูญหาย

| รายการ | ค่า |
| :--- | ---: |
| UDP Telemetry Port | 3334 |
| ระยะเวลาทดสอบ | 1 นาที |
| Received | 596 packets |
| Lost | 4 packets |
| Packets ที่ควรได้รับ | 600 packets |
| Packet Loss Rate | 0.67% |

```text
--- Statistics ---
Received: 596 packets
Lost: 4 packets
Packet Loss Rate: 0.67%
```

การคำนวณ:

```text
Packet Loss Rate (%) = Lost / (Received + Lost) × 100
                     = 4 / (596 + 4) × 100
                     = 0.67%
```

## 2. คำตอบคำถามท้ายการทดลอง

### ข้อ 1: เปรียบเทียบ UDP กับ HTTP RESTful

ผลการทดสอบเปรียบเทียบความหน่วงระหว่าง UDP Socket และ HTTP RESTful มีดังนี้:

| โปรโตคอล | Min RTT | Mean RTT | Max RTT |
| :--- | :---: | :---: | :---: |
| UDP Socket (10 รอบ) | 5.41 ms | 8.96 ms | 23.70 ms |
| HTTP REST (ใบงาน 10.1) | 24.80 ms | 44.60 ms | 182.30 ms |

UDP มี RTT ต่ำกว่า HTTP RESTful โดยทั่วไป เนื่องจากเป็นการสื่อสารแบบ Connectionless ใช้ Header ขนาดเล็ก และไม่มี TCP Handshake หรือ HTTP Request/Response Header จำนวนมาก จึงเหมาะกับ Telemetry แบบ Real-time และคำสั่งควบคุมที่ต้องการการตอบสนองรวดเร็ว

HTTP RESTful มี Overhead และความหน่วงสูงกว่า แต่มีโครงสร้างชัดเจน ใช้งานง่าย และอาศัย TCP ซึ่งช่วยรับประกันการส่งข้อมูล เหมาะกับข้อมูลที่ต้องการความถูกต้องและการตอบกลับที่เชื่อถือได้

จากผลการทดลอง UDP มีค่า Mean RTT ต่ำกว่า HTTP REST ประมาณ 5 เท่า (`8.96 / 44.60` หรือประมาณ `4.98` เท่า)

### ข้อ 2: วิเคราะห์ Packet Loss

จากการทดสอบเป็นเวลา 1 นาที ได้รับข้อมูล 596 แพ็กเก็ต และสูญหาย 4 แพ็กเก็ต คิดเป็น Packet Loss Rate เท่ากับ **0.67%**

สาเหตุที่อาจทำให้เกิด Packet Loss บนเครือข่าย Wi-Fi ได้แก่:

1. สัญญาณรบกวนและการชนกันของคลื่นความถี่ 2.4 GHz
2. UDP Broadcast ไม่มีการยืนยันการรับหรือการส่งซ้ำโดยอัตโนมัติ
3. การส่งข้อมูลด้วย Data Rate ต่ำสุดหรือสภาพสัญญาณไม่คงที่
4. กลไก Wi-Fi Power Save ของ ESP32
5. บัฟเฟอร์ของอุปกรณ์รับเต็มหรือโปรแกรมฝั่งรับประมวลผลไม่ทัน
6. Firewall หรือ Access Point กรอง UDP Broadcast

UDP ไม่มีการยืนยันการรับและไม่มีการส่งซ้ำโดยอัตโนมัติ ดังนั้นผู้ส่งอาจไม่ทราบว่าข้อมูลสูญหาย หากต้องการลดผลกระทบควรตรวจสอบ Sequence Number ส่งข้อมูลซ้ำสำหรับข้อมูลสำคัญ หรือเปลี่ยนคำสั่งสำคัญเป็น Unicast ที่มี ACK

### ข้อ 3: ข้อดีและข้อจำกัดของ Broadcast, Multicast และ Unicast

**UDP Broadcast (`255.255.255.255`)**

- **ข้อดี:** ไม่ต้องรู้ IP ปลายทาง และส่งข้อมูลครั้งเดียวให้อุปกรณ์ทุกเครื่องในเครือข่าย LAN ได้รับ เหมาะกับการค้นหาอุปกรณ์ (Discovery) และการประกาศ Telemetry
- **ข้อจำกัด:** ไม่สามารถข้ามเราเตอร์ได้ อุปกรณ์ทุกเครื่องต้องรับข้อมูลแม้ไม่ต้องการ ทำให้สิ้นเปลืองแบนด์วิดท์และพลังงาน ไม่มีการส่งซ้ำ และมักถูกบล็อกในเครือข่าย Wi-Fi ขององค์กร

**UDP Multicast**

ควรใช้เมื่อมีผู้รับหลายเครื่องแต่ไม่ใช่ทุกเครื่อง เช่น แดชบอร์ดหลายจอที่สมัครสมาชิกกลุ่ม `239.x.x.x` เพราะช่วยจำกัดกลุ่มผู้รับและลด Traffic เมื่อเทียบกับ Broadcast อย่างไรก็ตามต้องอาศัยการรองรับ Multicast จาก Router และ Access Point

**UDP Unicast**

ควรใช้เมื่อทราบ IP ปลายทางแล้ว หรือต้องการส่งคำสั่งควบคุมไปยังอุปกรณ์เฉพาะ เช่น คำสั่ง `LED_ON` และ `LED_OFF` ไปยัง ESP32 ที่ `10.14.195.186` เนื่องจากควบคุมปลายทางได้ชัดเจน ไม่รบกวนอุปกรณ์อื่น และสามารถรอรับ ACK เพื่อวัด RTT หรือยืนยันผลการทำงานได้
