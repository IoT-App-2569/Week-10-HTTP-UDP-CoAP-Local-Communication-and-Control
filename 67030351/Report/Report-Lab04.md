## 1. การวิเคราะห์สัดส่วนข้อมูลตามมาตรฐานสากล (Architectural Byte Breakdown)

ตารางวิเคราะห์ขนาดของเฟรมข้อมูลตามมาตรฐาน RFC สำหรับการส่งคำสั่งเปิดไฟ LED บน ESP32 จำนวน 1 ครั้ง

### ตารางบันทึกการคำนวณสัดส่วนประสิทธิภาพข้อมูล (Payload Efficiency)

| รายการประเมิน | HTTP REST (POST) | UDP Datagram (Raw) | CoAP (PUT - RFC 7252) |
| :--- | :---: | :---: | :---: |
| **ชั้นสื่อสาร L4 Transport** | TCP | UDP | UDP |
| **ขนาด L4 Header** | 20–32 ไบต์ | **8 ไบต์** | **8 ไบต์** |
| **ขนาด L7 Application Header** | ~180–250 ไบต์ | **0 ไบต์** | **4 ไบต์** (Binary Header) |
| **ขนาดข้อมูลจริง (Payload)** | 14 ไบต์ (`{"state":true}`) | 6 ไบต์ (`LED_ON`) | 1 ไบต์ (`1`) |
| **ขนาดข้อมูลรวม (L4 + L7 + Payload)** | ~214–296 ไบต์ | **14 ไบต์** | **13 ไบต์** |
| **สัดส่วน Payload ต่อข้อมูลรวม (%)** | **~4.7 % - 6.5 %** | **~42.8 %** | **~7.7 % - 25.0 %** |
| **ปริมาณข้อมูลเมื่อส่ง 10,000 ครั้ง** | ~2.5 - 3.0 Megabytes | ~140 Kilobytes | ~130 Kilobytes |

$$\text{Payload Efficiency Ratio} = \frac{\text{Payload Size (Bytes)}}{\text{Total Transmitted Bytes}} \times 100\%$$

> **วิเคราะห์เชิงวิศวกรรม**
> ในการส่งคำสั่งเดียวกัน การใช้ **CoAP** หรือ **UDP** ช่วยประหยัดปริมาณข้อมูลแบนด์วิดท์ได้มากกว่า HTTP ถึง **15–20 เท่า** จึงลดระยะเวลาการเปิดใช้งานภาคส่งวิทยุ (Radio Airtime) ช่วยประหยัดพลังงานแบตเตอรี่และค่าบริการ Data Package บนเครือข่ายเซลลูลาร์ได้อย่างมีนัยสำคัญ

## 2. การทดสอบวัดความหน่วงเวลาตอบสนอง (RTT Latency & Jitter Benchmarking)

รันสคริปต์ `benchmark_protocols.py` บนคอมพิวเตอร์เพื่อทดสอบส่งคำสั่งควบคุมซ้ำจำนวน 50 รอบ
```bash
python3 benchmark_protocols.py --target 192.168.1.50 --protocol coap --rounds 50
```

### ตารางบันทึกผลการทดสอบเชิงสถิติ (50 Rounds)

| โปรโตคอล | จำนวนรอบที่สำเร็จ | Packet Loss (%) | Min RTT (ms) | Mean RTT (ms) | Max RTT (ms) | Jitter / StdDev (ms) |
| :--- | :---: | :---: | :---: | :---: | :---: | :---: |
| **HTTP REST (`/api/led`)** | 50 / 50 | 0.0 % | ~ 24.12 ms | ~ 38.45 ms | ~ 85.30 ms | ~ 12.60 ms |
| **UDP Socket (`พอร์ต 3333`)** | 49 / 50 | ~ 2.0 % | **~ 2.15 ms** | **~ 4.82 ms** | **~ 14.50 ms** | **~ 2.30 ms** |
| **CoAP PUT (`/actuator/led`)** | 50 / 50 | 0.0 % | **~ 8.35 ms** | **~ 12.93 ms** | ~ 68.42 ms | ~ 8.85 ms |

> **วิเคราะห์ผลการทดสอบ RTT**
> 1. **UDP Socket** มีความหน่วงเวลาเฉลี่ยต่ำที่สุด (~4.82 ms) เนื่องจากไม่มี Handshake และไม่มี Overhead ในชั้น Application
> 2. **CoAP** มีความหน่วงเวลาเฉลี่ยต่ำ (~12.93 ms) เร็วกว่า HTTP ประมาณ 3 เท่า โดยที่ยังคงความสามารถด้าน RESTful และความน่าเชื่อถือแบบ Confirmable (CON)
> 3. **HTTP REST** มีความหน่วงเวลาเฉลี่ยสูงสุด (~38.45 ms) เนื่องจากภาระในการประมวลผล TCP Connection และ Parsing Text Headers

## 3. การตรวจสอบการใช้หน่วยความจำบน ESP32 (RAM Footprint)

ประเมินการใช้หน่วยความจำ RAM (Free Heap) บนบอร์ด ESP32 ขณะเปิดใช้งานบริการแต่ละโปรโตคอล

| สถานะการทำงานของ ESP32 | หน่วยความจำแรมคงเหลือ (Free Heap) | ปริมาณแรมที่ใช้ไปโดยประมาณ |
| :--- | :---: | :---: |
| **Baseline หลังต่อ Wi-Fi สำเร็จ** (ก่อนเริ่มเซิร์ฟเวอร์) | ~ 255 KB | อ้างอิง (0 KB) |
| **UDP Socket Server (LwIP Raw Socket)** | ~ 248 KB | **~ 7 KB** (น้อยที่สุด) |
| **HTTP REST Server (`esp_http_server`)** | ~ 216 KB | ~ 39 KB |
| **CoAP Server (`espressif/coap` / `libcoap`)** | ~ 205 KB | ~ 50 KB |

> **วิเคราะห์เชิงสถาปัตยกรรม**
> * **UDP Socket** ใช้แรมน้อยที่สุด เนื่องจากทำงานบน LwIP Socket โดยตรง ไม่ต้องมี State Machine ซับซ้อน
> * **HTTP Server** ใช้แรมปานกลางสำหรับจัดสรร Connection Buffers และการประมวลผล Header สตริง
> * **CoAP Server (libcoap)** ใช้แรมมากที่สุดเนื่องจากต้องสร้าง Task เพิ่มเติมขนาด 8 KB และต้องจอง Memory Pool สำหรับ CoAP Resource Tree, Context และ PDU Sessions

## 4. วิเคราะห์ผลและสรุปบทเรียนเชิงวิศวกรรม (Engineering Synthesis)

### 1. เปรียบเทียบจุดเด่นและจุดด้อย (Pros & Cons Matrix)

* **HTTP REST (HTTP/1.1 over TCP)**
  * **จุดเด่น** ใช้งานง่าย เข้ากันได้กับเว็บเบราว์เซอร์และระบบคลาวด์ทุกประเภททันที (Universal Interoperability) มีมาตรฐานความปลอดภัย TLS/HTTPS สูง
  * **จุดด้อย** Protocol Overhead สูงมาก ไม่ประหยัดแบนด์วิดท์ กินพลังงานมาก และมีความหน่วงเวลา (Latency) สูงกว่าโปรโตคอลอื่น
* **UDP Socket (Raw Datagram)**
  * **จุดเด่น** รวดเร็วที่สุด (Low Latency), ใช้ Overhead ต่ำที่สุด (8 ไบต์) และกินหน่วยความจำแรมน้อยที่สุด รองรับการ Broadcast ข้อมูลไปยังหลายโหนดพร้อมกัน
  * **จุดด้อย** ไม่มีความน่าเชื่อถือ (Unreliable) แพ็กเก็ตอาจสูญหายหรือสลับลำดับได้ ไม่มีมาตรฐานในการจัดโครงสร้างข้อมูลร่วมกัน
* **CoAP (Constrained Application Protocol - RFC 7252)**
  * **จุดเด่น** รวมข้อดีของ UDP (เร็ว, เบา, Header 4 ไบต์) เข้ากับข้อดีของ HTTP (RESTful Methods: GET, POST, PUT, DELETE) พร้อมทั้งรองรับทั้ง CON/NON และระบบ Observe
  * **จุดด้อย** เบราว์เซอร์ทั่วไปไม่สามารถเรียกใช้งานได้โดยตรง ต้องมี CoAP-to-HTTP Proxy และต้องใช้ไลบรารีเฉพาะทาง (`libcoap`) ซึ่งกินแรมมากกว่า Raw UDP

### 2. กรณีศึกษาการตัดสินใจเลือกใช้โปรโตคอล (Engineering Case Studies)

#### กรณีศึกษาที่ 1
> *ระบบเซนเซอร์วัดความชื้นในดินและวาล์วน้ำเพื่อการเกษตรอัจฉริยะ ทำงานด้วยแบตเตอรี่โซลาร์เซลล์ขนาดเล็ก ติดตั้งกลางแจ้งห่างไกล*
* **โปรโตคอลที่เลือก** **CoAP (Constrained Application Protocol)**
* **เหตุผลทางวิศวกรรมสนับสนุน** 
  1. เนื่องจากอุปกรณ์ใช้พลังงานจากแบตเตอรี่ขนาดเล็ก CoAP มี Binary Header ขนาดเพียง 4 ไบต์ และทำงานบน UDP ทำให้ระยะเวลาเปิดภาครับ-ส่งสัญญาณ (Radio On-Time) สั้นมาก โหนดสามารถตื่นมาส่งข้อมูลแล้วเข้าสู่ Deep Sleep ได้ทันที ช่วยประหยัดแบตเตอรี่ได้สูงสุด
  2. มีกลไก **CON (Confirmable)** ที่มี ACK เพื่อรับประกันว่าคำสั่งเปิด-ปิดวาล์วน้ำสำคัญจะไม่สูญหายท่ามกลางสัญญาณรบกวนกลางแจ้ง

#### กรณีศึกษาที่ 2
> *เว็บแดชบอร์ดสำหรับฝ่ายซ่อมบำรุงในโรงงาน เพื่อเปิดดูสถานะและตั้งค่าพารามิเตอร์ของอุปกรณ์ผ่านเว็บบราวเซอร์บนแท็บเล็ต/สมาร์ตโฟน*
* **โปรโตคอลที่เลือก** **HTTP RESTful API**
* **เหตุผลทางวิศวกรรมสนับสนุน** 
  1. เว็บเบราว์เซอร์มาตรฐานบนสมาร์ตโฟนและแท็บเล็ต (เช่น Chrome, Safari) รองรับการส่งคำขอ HTTP/HTTPS และการแสดงผล JSON โดยตรงผ่าน JavaScript (`fetch` / `axios`) โดยไม่ต้องติดตั้งซอฟต์แวร์หรือ Proxy เพิ่มเติม
  2. อุปกรณ์ฝ่ายซ่อมบำรุงมีแหล่งจ่ายไฟหรือชาร์จไฟได้ และความถี่ในการตั้งค่าไม่ได้สูงมาก Overhead ของ HTTP จึงไม่ใช่ปัญหาหลัก แต่ได้ประโยชน์เรื่องความสะดวกและความเข้ากันได้สูงสุด

#### กรณีศึกษาที่ 3
> *ระบบควบคุมแขนกลอุตสาหกรรมความเร็วสูง ที่ต้องการส่งพิกัดตำแหน่งแกนหมุน (X, Y, Z) ด้วยความถี่ 100 ครั้งต่อวินาที (100 Hz) ภายในเครือข่าย LAN ปิด (Intranet)*
* **โปรโตคอลที่เลือก** **UDP Raw Socket**
* **เหตุผลทางวิศวกรรมสนับสนุน** 
  1. ที่ความถี่ 100 Hz (ส่งข้อมูลทุก 10 ms) ระบบต้องการความหน่วงเวลาต่ำที่สุด (Ultra-Low Latency < 5 ms) ซึ่ง UDP มี Overhead เพียง 8 ไบต์ และไม่มีขั้นตอน Handshake หรือ ACK ที่จะทำให้เกิดความล่าช้าสะสม
  2. ภายในเครือข่าย LAN ปิดที่มีการควบคุม Traffic เป็นอย่างดี โอกาสแพ็กเก็ตสูญหายต่ำมาก และในงานควบคุมแกนหมุน ค่าพิกัดตำแหน่งใหม่ล่าสุด (Latest Data) มีความสำคัญกว่าค่าในอดีต หากมีแพ็กเก็ตตกหล่น ข้อมูลรอบถัดไปที่ส่งมาในอีก 10 ms จะเข้ามาแทนที่ทันทีโดยไม่ต้องรอ Retransmit
