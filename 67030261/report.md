#### 1. ตรวจสอบ mDNS ด้วยคำสั่ง ping
เปิด Terminal บนเครื่องคอมพิวเตอร์ที่อยู่ในวง Wi-Fi เดียวกัน
```powershell
ping esp32-node.local
```
*(บันทึกภาพผลการ Ping และหมายเลข IP ที่ Resolve ได้ เช่น `Reply from 192.168.1.181`)*

> [!TIP] **คู่มือการแก้ไขปัญหาเมื่อ Resolve ชื่อ `esp32-node.local` ไม่พบ (Troubleshooting Guide)**
> หากคำสั่ง `ping esp32-node.local` ขึ้นข้อความ `could not find host` ให้ตรวจสอบ 2 จุดสำคัญดังนี้
> 1. **เปลี่ยนสถานะ Wi-Fi บน Windows เป็น "Private Network"**
>    เปิด **Settings** $\rightarrow$ **Network & internet** $\rightarrow$ **Wi-Fi** $\rightarrow$ คลิกที่ชื่อเครือข่าย Wi-Fi ที่เชื่อมต่อ $\rightarrow$ เปลี่ยนจาก **Public network** เป็น **Private network** (เนื่องจาก Public network บน Windows จะสั่ง Firewall บล็อกแพ็กเก็ต mDNS UDP 5353 ขาเข้าทั้งหมด)
> 2. **ปิดหรือถอดสาย LAN ที่ต่อซ้อนอยู่**
>    หากเครื่องคอมพิวเตอร์เสียบสาย LAN ไว้ด้วย Windows จะจัดลำดับ Routing Metric ให้สาย LAN สูงกว่า Wi-Fi เสมอ ทำให้แพ็กเก็ต Multicast (`224.0.0.251`) ถูกส่งออกไปทางสาย LAN แทนที่จะเป็น Wi-Fi ที่ ESP32 เกาะอยู่ ให้ปิด (Disable) การ์ดแลนหรือถอดสาย LAN ออกชั่วคราวขณะทดสอบ mDNS

#### 2. ทดสอบอ่านค่าเซนเซอร์ผ่าน cURL
เปิด PowerShell แล้วรันคำสั่ง (แนะนำให้พิมพ์ `curl.exe` เพื่อเรียกใช้โปรแกรม cURL แท้ของระบบแทน PowerShell Alias)
```powershell
curl.exe -X GET http://esp32-node.local/api/status
```
ผลลัพธ์ที่ได้จะเป็น JSON Payload เช่น
```json
{"pot_raw":15,"free_heap":213848,"led":true}
```

#### 3. ทดสอบสั่งเปิด-ปิด LED ผ่าน cURL หรือ PowerShell

**วิธีที่ 1 ใช้ `curl.exe` (ครอบสตริง JSON ด้วย Single Quote เพื่อป้องกัน PowerShell ตัดเครื่องหมายคำพูด)**
```powershell
# สั่งเปิดไฟ LED (GPIO 2)
curl.exe -s -X POST http://esp32-node.local/api/led -H "Content-Type: application/json" -d '{\"state\": true}'
curl http://esp32-node.local/api/led -H "Content-Type: application/json" -d '{\"state\": true}'
# สั่งปิดไฟ LED (GPIO 2)
curl.exe -s -X POST http://esp32-node.local/api/led -H "Content-Type: application/json" -d '{\"state\": false}'
curl http://esp32-node.local/api/led -H "Content-Type: application/json" -d '{\"state\": false}'
```
การเปิดและปิดไฟ จะได้ผลลัพธ์เป็น `{"result":"success"}` ทั้งคู่

**วิธีที่ 2 ใช้คำสั่ง `Invoke-RestMethod` ของ PowerShell โดยตรง (แนะนำสำหรับ Windows)**
```powershell
# สั่งเปิดไฟ LED
Invoke-RestMethod -Uri "http://esp32-node.local/api/led" -Method POST -ContentType "application/json" -Body '{"state": true}'

Invoke-RestMethod -Uri "http://esp32-node.local/api/led" -Method POST -ContentType "application/json" -Body '{"state": false}'
```

## 4. บันทึกผลการทดลองและคำถามท้ายการทดลอง 
1. นำผลการวัดค่า RTT Latency ของ UDP ในกิจกรรมที่ 10-2.5 มาเปรียบเทียบกับความหน่วงเวลาของ HTTP RESTful ในใบงาน 10.1 และวิเคราะห์ความแตกต่าง

```
UDP รันซ้ำอีกรอบหลังแฟลชกลับ เฉลี่ย 41.30 ms มัธยฐาน 22.29 ต่ำสุด 10.00 สูงสุด 180.24
HTTP GET /api/status เฉลี่ย 141.32 ms มัธยฐาน 92.85 ต่ำสุด 56.65 สูงสุด 565.77
HTTP POST /api/led เฉลี่ย 157.21 ms มัธยฐาน 97.20 ต่ำสุด 70.29 สูงสุด 746.20
ในส่วน GET เฉพาะขั้นเปิดการเชื่อมต่อ TCP อย่างเดียวใช้เฉลี่ย 70.40 ms

เทียบกัน
ถ้าใช้มัธยฐาน UDP โดยไม่สนใจค่าแปลกๆ อยู่ที่ประมาณ 22 ms ส่วน HTTP ประมาณ 93 ถึง 97 ms คือช้ากว่าประมาณ 4 เท่า ถ้าใช้ค่าเฉลี่ย HTTP ช้ากว่า UDP ประมาณ 3.4 ถึง 4.5 เท่า

วิเคราะห์
- ความต่างหลักมาจาก TCP handshake ที่ต้องแลก 3 ทาง ก่อนส่งคำขอจริง ขั้นนี้อย่างเดียวก็กินไปครึ่งหนึ่งของเวลา HTTP ทั้งหมดแล้ว ส่วน UDP ส่งแล้วรอตอบเลย รอบเดียว
- HTTP ต้องแลกข้อความมากกว่า ทั้ง header 71 ไบต์ ตัว JSON และการปิดการเชื่อมต่อ ส่วน UDP แพ็กเก็ตมีแค่ข้อความสั้นๆ กับ ACK
- ค่าสูงสุดของ HTTP ถึง 565 และ 746 ms เพราะ TCP ต้อง retransmit เมื่อแพ็กเก็ตหายบน Wi-Fi ที่ไม่เสถียร ขณะที่ UDP ไม่มี retransmit จึงสูงสุดแค่ 75 ถึง 180 ms
- ข้อแลกเปลี่ยนคือ UDP เร็วกว่าแต่ไม่รับประกันการส่งถึง ตามผลข้อ 2 ที่หายถึง 14 เปอร์เซ็นต์ ส่วน HTTP ช้ากว่าแต่ข้อมูลครบแน่นอน
```

```
สาเหตุที่แพ็กเก็ตหายบน Wi-Fi
- ใช้ฮอตสปอตมือถือ IP 172.20.10.x ซึ่งไม่ได้ออกแบบมาให้รับ broadcast ถี่ๆ และสัญญาณไม่นิ่งเท่า router จริง
- UDP broadcast ไม่มี ACK และไม่มี retransmit AP ไม่ส่งซ้ำให้ ถ้าชนหรือโดนรบกวนก็หายเลย
- Wi-Fi ย่าน 2.4 GHz แย่งช่องสัญญาณกับอุปกรณ์อื่น เกิดการชนกันของคลื่น
- broadcast มักถูกส่งด้วยอัตราบิตต่ำสุดและไม่ได้รับการรับประกันเหมือน unicast
- ฝั่งรับหรือบัฟเฟอร์ของ AP อาจทิ้งแพ็กเก็ตตอนทราฟฟิกหนาแน่น

วิธีลด loss
- ย้ายไปใช้ router จริง ขยับบอร์ดใกล้ AP ใช้ unicast แทน broadcast หรือถ้าต้องไม่ให้ข้อมูลหาย ก็ต้องเพิ่มกลไกยืนยันเองในแอปพลิเคชัน
```
3. อธิบายข้อดีและข้อจำกัดของการใช้ `255.255.255.255` (UDP Broadcast) ในระบบ IoT และในสถานการณ์ใดที่ควรเปลี่ยนไปใช้ **UDP Multicast** หรือ **Unicast** แทน?
```
ข้อดีของ 255.255.255.255 คือง่าย ไม่ต้องรู้ IP ผู้รับ ส่งทีเดียวทุกเครื่องในวงเดียวกันได้รับหมด เหมาะกับการประกาศตัวหรือ telemetry ที่ใครอยากฟังก็ฟัง
ข้อจำกัดคือถูกกระจายไปทุกเครื่อง แม้เครื่องที่ไม่สนใจก็ต้องรับและประมวลผล, ข้าม router หรือ subnet ไม่ได้, บาง AP ส่ง broadcast ด้วยอัตราต่ำสุดทำให้เปลืองแอร์ไทม์, และไม่มีความปลอดภัย ใครก็ดักอ่านได้
ควรเปลี่ยนไปใช้ multicast เมื่อมีผู้รับหลายเครื่องแต่ไม่ใช่ทั้งวง ให้เครื่องที่สนใจเข้า group เองเท่านั้น และใช้ unicast เมื่อมีผู้รับเครื่องเดียว หรือต้องการ ACK และความน่าเชื่อถือ เช่นคำสั่งควบคุม LED
```

## 4. บันทึกผลการทดลองและคำถามท้ายบท (Lab Report & Questions)
1. นำผลการ Query `/.well-known/core` มาแสดงในรายงาน พร้อมอธิบายรูปแบบ **CoRE Link Format (RFC 6690)** ว่าแสดงข้อมูลทรัพยากรอย่างไร

```
ผลที่ได้
  </sensor/pot>,</actuator/led>

อธิบายรูปแบบ CoRE Link Format ตาม RFC 6690
เป็นข้อความธรรมดาที่แต่ละทรัพยากรเป็นหนึ่งลิงก์ ใส่ URI ไว้ในเครื่องหมาย < > แล้วคั่นแต่ละลิงก์ด้วยจุลภาค ในผลนี้มี 2 ทรัพยากรคือ /sensor/pot กับ /actuator/led ถ้าต้องการบอกรายละเอียดเพิ่ม ให้ต่อท้ายแต่ละลิงก์ด้วยแอตทริบิวต์คั่นด้วยเซมิโคลอน เช่น rt คือชนิดของทรัพยากร ct คือชนิดเนื้อหา if คืออินเทอร์เฟซ obs คือรองรับ Observe ตอนนี้โค้ดยังไม่ได้ใส่แอตทริบิวต์ จึงเห็นแค่ URI ประโยชน์คือไคลเอนต์ถามทีเดียวก็รู้ว่าโหนดมีอะไรให้ใช้ ไม่ต้องรู้ล่วงหน้า
```

2. อธิบายความแตกต่างของแพ็กเก็ต CoAP ระหว่าง **CON (Confirmable)** และ **NON (Non-confirmable)** เมื่อทดสอบในเครือข่ายที่มีการรบกวนสัญญาณ

```
CON คือ Confirmable ผู้รับต้องตอบ ACK กลับ ถ้าผู้ส่งไม่ได้ ACK ภายในเวลาที่กำหนดจะส่งซ้ำเองด้วย exponential backoff จึงการันตีว่าถึง แต่ใช้เวลาและแพ็กเก็ตเพิ่มเมื่อสัญญาณถูกรบกวน
NON คือ Non-confirmable ส่งทีเดียวไม่มี ACK ไม่ส่งซ้ำ ถ้าหายก็หาย เบากว่าและเหมาะกับค่าเซนเซอร์ที่ส่งถี่ๆ ที่ค่าเก่าไม่มีความหมายแล้ว

เมื่อทดสอบในเครือข่ายที่มีการรบกวนสัญญาณ CON การันตีข้อมูลถึง แลกกับความหน่วงที่พุ่งขึ้นและแพ็กเก็ตที่ส่งซ้ำเพิ่ม NON ไม่เพิ่มภาระและหน่วงน้อย แต่ข้อมูลหายได้ เหมาะกับค่าเซนเซอร์ที่ส่งถี่ 
```

3. ทำไม CoAP จึงเหมาะสมกับโปรโตคอลการสื่อสารบนเครือข่ายเช่น Thread, Zigbee IP หรือ NB-IoT มากกว่า HTTP?

```
เครือข่ายเหล่านี้แบนด์วิดท์ต่ำ แพ็กเก็ตเล็ก อุปกรณ์ใช้แบตเตอรี่และ RAM น้อย
HTTP รันบน TCP ที่ต้องทำ handshake สามทางก่อนส่งข้อมูล และ header ใหญ่ ซึ่งในแล็บ 10.1 วัดได้ 71 ไบต์ ต่อ body แค่ 44 ไบต์
CoAP รันบน UDP header คงที่ 4 ไบต์ ใช้ตัวเลือกแบบไบนารีกะทัดรัด ไม่ต้องรักษาการเชื่อมต่อค้างไว้ ประหยัดพลังงานเพราะอุปกรณ์หลับได้ มี CON กับ NON ให้เลือกความน่าเชื่อถือตามงาน มี Observe ให้ส่งค่าเมื่อเปลี่ยนแทนการ poll และแปลงเป็น HTTP ผ่านตัวกลางได้ จึงยังได้สถาปัตยกรรม REST เหมือนเดิม
```

## 4. วิเคราะห์ผลและสรุปบทเรียนเชิงวิศวกรรม (Engineering Synthesis)

ให้นักศึกษาตอบคำถามเชิงวิเคราะห์ต่อไปนี้ลงในรายงานการทดลอง

### 1. เปรียบเทียบจุดเด่นและจุดด้อย (Pros & Cons Matrix)
จงสรุปข้อดีและข้อจำกัดของ **HTTP, UDP, และ CoAP** จากผลการทดลองจริง 
* **HTTP** 
```
ข้อดี มาตรฐานที่ทุกแพลตฟอร์มรองรับ ทดสอบได้ด้วย cURL หรือเบราว์เซอร์ ใช้ JSON อ่านง่าย รับประกันข้อมูลถึงเพราะอยู่บน TCP
ข้อจำกัด ช้าที่สุดในการวัด (mean 209.95 ms, median 112.32 ms) เพราะต้องทำ TCP handshake ทุกครั้ง header ใหญ่เกินข้อมูล (71 ไบต์ต่อ 44 ไบต์) และ Max ถึง 1334.78 ms เมื่อต้อง retransmit จึงไม่เหมาะกับอุปกรณ์แบตเตอรี่หรือเครือข่ายแบนด์วิดท์ต่ำ
```
* **UDP** 
```
ข้อดี เร็วที่สุด (min 11.28 ms, median 43.60 ms) ไม่มี handshake และ overhead ต่ำ ส่ง broadcast หรือสตรีม telemetry ถี่ๆ ได้
ข้อจำกัด ไม่รับประกันการส่งถึงและไม่เรียงลำดับ ต้องออกแบบ ACK, sequence number และ retry เอง ผล broadcast 1 นาทีหายถึง 14.06 % ไม่มีความปลอดภัยในตัว และ jitter สูง (StdDev 126.45 ms) ตามสภาพ Wi-Fi
```
* **CoAP**
```
ข้อดี header เล็กเพียง 4 ไบต์ ใช้ UDP แต่เลือกความน่าเชื่อถือได้ ตอนยิง 150 คำขอพร้อมกัน CON ครบ 100 % ส่วน NON เร็วแต่หาย 95.3 % มี Discovery (/.well-known/core) และ Observe แมปกับ REST/HTTP ได้ jitter ต่ำสุดในสามตัว (StdDev 90.54 ms)
ข้อจำกัด ต้องใช้ไลบรารีหรือเครื่องมือเฉพาะ เบราว์เซอร์เรียกตรงไม่ได้ CON ซ่อนการสูญหายด้วยการส่งซ้ำ แลกกับ latency ที่พุ่ง (เฉลี่ย 2065 ms ตอนโหลดหนัก) และ RTT ที่วัดในแล็บนี้รวม overhead ของไลบรารี aiocoap จึงไม่ควรสรุปว่า CoAP ช้ากว่าด้วยตัวโปรโตคอลเอง
```
### 2. กรณีศึกษาการตัดสินใจเลือกใช้โปรโตคอล (Engineering Case Studies)
หากท่านเป็นหัวหน้าวิศวกรออกแบบระบบ IoT จงเลือกโปรโตคอลที่เหมาะสมที่สุดสำหรับแต่ละกรณีศึกษาต่อไปนี้ พร้อมให้เหตุผลทางวิศวกรรมสนับสนุน

* **กรณีศึกษาที่ 1** *ระบบเซนเซอร์วัดความชื้นในดินและวาล์วน้ำเพื่อการเกษตรอัจฉริยะ ทำงานด้วยแบตเตอรี่โซลาร์เซลล์ขนาดเล็ก ติดตั้งกลางแจ้งห่างไกล*
  * **โปรโตคอลที่เลือก** CoAP ส่งค่าเซนเซอร์แบบ NON ส่งคำสั่งวาล์วแบบ CON
  * **เหตุผลทางวิศวกรรม** พลังงานและแบนด์วิดท์จำกัด CoAP มี header เพียง 4 ไบต์ ไม่ต้องรักษา TCP connection อุปกรณ์จึงหลับได้ระหว่างส่งข้อมูลและรองรับเครือข่ายพลังงานต่ำอย่าง NB-IoT หรือ Thread ค่าความชื้นเปลี่ยนช้า ถ้าหายสักค่าก็ไม่เสียหาย ใช้ NON ประหยัดพลังงาน ส่วนคำสั่งเปิดปิดวาล์วต้องแน่ใจว่าถึง จึงใช้ CON ที่มี ACK และส่งซ้ำอัตโนมัติ (ผลทดสอบ CON ครบ 100 % แม้ NON หาย 95.3 %) และ Observe ช่วยให้ส่งค่าเฉพาะเมื่อเปลี่ยน ไม่ต้อง poll
    
* **กรณีศึกษาที่ 2** *เว็บแดชบอร์ดสำหรับฝ่ายซ่อมบำรุงในโรงงาน เพื่อเปิดดูสถานะและตั้งค่าพารามิเตอร์ของอุปกรณ์ผ่านเว็บบราวเซอร์บนแท็บเล็ต/สมาร์ตโฟน*
  * **โปรโตคอลที่เลือก** HTTP (REST + JSON)
  * **เหตุผลทางวิศวกรรม** เบราว์เซอร์รองรับ HTTP โดยตรง ไม่ต้องติดตั้งโปรแกรมเพิ่ม ใช้ได้กับทุกอุปกรณ์ และต่อยอดด้วย HTTPS, การยืนยันตัวตน และเครื่องมือดีบั๊กที่พร้อมใช้ ผู้ใช้เป็นคนที่ตอบสนองระดับวินาที ความหน่วงราว 100 ms (median 112.32 ms ในการวัด) ไม่เป็นปัญหา และข้อมูลต้องถึงครบ ซึ่ง TCP รับประกันให้ ส่วน overhead ที่ใหญ่ไม่สำคัญเพราะอุปกรณ์ฝั่งผู้ใช้ไม่ใช่ตัวที่จำกัดพลังงาน

* **กรณีศึกษาที่ 3** *ระบบควบคุมแขนกลอุตสาหกรรมความเร็วสูง ที่ต้องการส่งพิกัดตำแหน่งแกนหมุน (X, Y, Z) ด้วยความถี่ 100 ครั้งต่อวินาที (100 Hz) ภายในเครือข่าย LAN ปิด (intranet)*
  * **โปรโตคอลที่เลือก** UDP (แบบ unicast พร้อม sequence number)
  * **เหตุผลทางวิศวกรรม** ที่ 100 Hz มีเวลาแค่ 10 ms ต่อรอบ HTTP ทำไม่ได้เพราะแค่ handshake ก็เกินแล้ว (RTT ที่วัดได้หลายสิบถึงร้อยกว่า ms) CoAP แบบ CON เพิ่ม ACK ต่อทุกแพ็กเก็ตและอาจส่งซ้ำนานเกินรอบควบคุม การส่งพิกัดซ้ำเป็นข้อมูลล้าสมัยไปแล้ว ถ้าหายหนึ่งตัวก็รอตัวถัดไปใน 10 ms ได้ ไม่ควรรอส่งซ้ำ UDP จึงเหมาะที่สุด ใช้ sequence number ตรวจแพ็กเก็ตหายและทิ้งตัวที่มาช้า ใช้ unicast แทน broadcast เพื่อไม่รบกวนอุปกรณ์อื่น ข้อควรระวังคือ ผลวัดบน Wi-Fi มี jitter สูง (StdDev 126.45 ms) และ broadcast หาย 14.06 % จึงควรใช้สาย Ethernet ใน LAN ปิดจริง ไม่ใช้ Wi-Fi
