### 3. วิเคราะห์ผลและสรุปบทเรียนเชิงวิศวกรรม (Engineering Synthesis)

#### 1. เปรียบเทียบจุดเด่นและจุดด้อย (Pros & Cons Matrix)

* **HTTP (HyperText Transfer Protocol):**
  * **จุดเด่น (Pros):** รองรับโดยสากลทุกแพลตฟอร์ม, ใช้งานร่วมกับ Web Browser ได้โดยตรงโดยไม่ต้องลงแอปเพิ่ม, โครงสร้าง RESTful API และ JSON เข้าใจง่าย ดีบั๊กสะดวกด้วย cURL หรือ Postman, ความปลอดภัยสูงด้วย HTTPS/TLS
  * **จุดด้อย (Cons):** Overhead สูงมาก (ส่วนหัวเป็นข้อความ ASCII ขนาดใหญ่), Latency สูงจากสแตก TCP 3-Way Handshake, สิ้นเปลืองพลังงานและแรมบน ESP32 สูง ไม่เหมาะกับอุปกรณ์พลังงานแบตเตอรี่

* **UDP (User Datagram Protocol):**
  * **จุดเด่น (Pros):** ความหน่วงต่ำที่สุดในระดับ Real-time (< 3 ms), ความแปรปรวน (Jitter) ต่ำมาก, กินแรมน้อยที่สุด (~7 KB), รองรับการส่งแบบ Broadcast/Multicast ข้อมูลไปยังหลายโฮสต์พร้อมกันในคำสั่งเดียว
  * **จุดด้อย (Cons):** ไม่รับประกันการส่งข้อมูล (No ACK / Retransmission), ข้อมูลอาจสูญหายหรือสลับลำดับได้, ไม่มีมาตรฐาน Application Layer โครงสร้างคำสั่งต้องเขียนโปรโตคอลจัดการเองทั้งหมด

* **CoAP (Constrained Application Protocol - RFC 7252):**
  * **จุดเด่น (Pros):** ผสานข้อดีของ RESTful (GET/PUT/POST) เข้ากับความเบาของ UDP, ขนาด Header เพียง 4 ไบต์, สามารถเลือกความน่าเชื่อถือได้ทั้ง CON (มีการ ACK และส่งซ้ำ) และ NON (ส่งเร็ว), มีระบบ Resource Discovery และ Observe (Pub/Sub) ในตัว, ประหยัดพลังงานแบตเตอรี่สูงสุด
  * **จุดด้อย (Cons):** เว็บบราวเซอร์ทั่วไปไม่สามารถเชื่อมต่อได้โดยตรง ต้องอาศัย CoAP Gateway หรือ Reverse Proxy แปลงเป็น HTTP, เครื่องมือและไลบรารีบนแพลตฟอร์มคอมพิวเตอร์ทั่วไปมีน้อยกว่า HTTP

#### 2. กรณีศึกษาการตัดสินใจเลือกใช้โปรโตคอล (Engineering Case Studies)

#### กรณีศึกษาที่ 1:
> **โจทย์:** ระบบเซนเซอร์วัดความชื้นในดินและวาล์วน้ำเพื่อการเกษตรอัจฉริยะ ทำงานด้วยแบตเตอรี่โซลาร์เซลล์ขนาดเล็ก ติดตั้งกลางแจ้งห่างไกล
* **โปรโตคอลที่เลือก:** **CoAP (ร่วมกับ NB-IoT หรือ 6LoWPAN / Thread)**
* **เหตุผลทางวิศวกรรม:**
  1. เนื่องจากอุปกรณ์ใช้แบตเตอรี่ร่วมกับโซลาร์เซลล์ขนาดเล็ก หัวใจสำคัญคือการประหยัดพลังงาน (Low Power Consumption) และการเข้าสู่โหมดหลับลึก (Deep Sleep) ให้เร็วที่สุด
  2. CoAP มี Overhead ต่ำมาก (Header 4 ไบต์) และทำงานบน UDP ทำให้โหนดใช้เวลาตื่นมาส่งข้อมูลเพียงไม่กี่มิลลิวินาทีแล้วหลับทันที โดยไม่ต้องสิ้นเปลืองพลังงานทำ TCP Handshake เหมือน HTTP
  3. สำหรับคำสั่งควบคุมเปิด-ปิดวาล์วน้ำที่มีความสำคัญสูง สามารถเลือกส่งแพ็กเก็ตแบบ **CON (Confirmable)** เพื่อให้แน่ใจว่าวาล์วได้รับคำสั่งจริงและมีการส่งซ้ำหากแพ็กเก็ตตกหล่น

#### กรณีศึกษาที่ 2:
> **โจทย์:** เว็บแดชบอร์ดสำหรับฝ่ายซ่อมบำรุงในโรงงาน เพื่อเปิดดูสถานะและตั้งค่าพารามิเตอร์ของอุปกรณ์ผ่านเว็บบราวเซอร์บนแท็บเล็ต/สมาร์ตโฟน
* **โปรโตคอลที่เลือก:** **HTTP RESTful API (ร่วมกับ mDNS Service Discovery)**
* **เหตุผลทางวิศวกรรม:**
  1. ไคลเอนต์ปลายทางคือฝ่ายช่างที่ใช้เว็บบราวเซอร์ (Chrome, Safari) บนแท็บเล็ตหรือสมาร์ตโฟน ซึ่งรองรับโปรโตคอล HTTP และ JSON โดยกำเนิด ทำให้ไม่ต้องติดตั้งแอปพลิเคชันเสริม
  2. การใช้ **mDNS** ช่วยให้ช่างสามารถพิมพ์ชื่อ Hostname จำง่าย เช่น `http://machine-01.local` หรือ `http://sensor-press-a.local` บน URL bar เพื่อเข้าถึงหน้าแดชบอร์ดได้ทันทีโดยไม่ต้องจำ IP Address
  3. สถาปัตยกรรม RESTful API มีความยืดหยุ่นสูง รองรับการอ่านค่าสถานะ (`GET /api/status`) และการเปลี่ยนค่าคอนฟิก (`POST /api/config`) ผ่านฟอร์มเว็บได้อย่างสะดวกและปลอดภัย

#### กรณีศึกษาที่ 3:
> **โจทย์:** ระบบควบคุมแขนกลอุตสาหกรรมความเร็วสูง ที่ต้องการส่งพิกัดตำแหน่งแกนหมุน (X, Y, Z) ด้วยความถี่ 100 ครั้งต่อวินาที (100 Hz) ภายในเครือข่าย LAN ปิด (intranet)
* **โปรโตคอลที่เลือก:** **UDP Socket (Unicast หรือ Multicast)**
* **เหตุผลทางวิศวกรรม:**
  1. ความถี่ 100 Hz หมายถึงมีรอบการส่งข้อมูลทุกๆ **10 มิลลิวินาที** ต้องการความหน่วงเวลาต่ำมาก (Ultra-low Latency < 2 ms) และความแปรปรวน (Jitter) ต่ำสุด ซึ่ง UDP ให้ความเร็วสูงและไม่มีภาระการรอ ACK
  2. ในระบบ Real-time Motion Control ข้อมูลพิกัดตำแหน่งเป็นข้อมูลแบบ *Temporal Data (ข้อมูลอิงเวลา)* หากแพ็กเก็ตใดเกิดตกหล่นไป ไม่มีความจำเป็นต้องส่งซ้ำ (No Retransmission) เพราะข้อมูลพิกัดชุดใหม่จะถูกส่งมาทดแทนทันทีในอีก 10 มิลลิวินาทีถัดไป การใช้ TCP จะทำให้เกิดปัญหา **Head-of-Line Blocking** ซึ่งจะทำให้แขนกลกระตุกอย่างรุนแรง
  3. ทำงานในเครือข่าย LAN ปิด (Dedicated Industrial Intranet) ซึ่งมีความเสถียรของสายสื่อสารสูง อัตราการสูญหายของแพ็กเก็ตต่ำมาก UDP จึงเป็นตัวเลือกที่สมบูรณ์แบบที่สุด
