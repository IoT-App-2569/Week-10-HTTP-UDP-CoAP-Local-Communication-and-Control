## 4. บันทึกผลการทดลองและคำถามท้ายการทดลอง 
1. นำผลการวัดค่า RTT Latency ของ UDP ในกิจกรรมที่ 10-2.5 มาเปรียบเทียบกับความหน่วงเวลาของ HTTP RESTful ในใบงาน 10.1 และวิเคราะห์ความแตกต่าง
* **UDP Socket** มีค่า RTT Latency เฉลี่ย **21.89 ms** (Min 2.72 ms, Max 75.04 ms) แต่ถ้าตัดรอบที่ค่ากระโดด 3 รอบ (58.45, 75.04, 51.59 ms) ออก ค่าเฉลี่ยปกติอยู่ที่ประมาณ **4.84 ms** ซึ่งต่ำมาก เพราะ UDP เป็นโปรโตคอลแบบ Connectionless
  * ส่งคำสั่งได้ทันทีในแพ็กเก็ตเดียว ไม่ต้องทำ 3-Way Handshake (SYN, SYN-ACK, ACK) และไม่ต้องปิดการเชื่อมต่อ
  * ใช้เพียง 1 รอบไป-กลับต่อคำสั่ง คือส่ง `LED_ON` แล้วรับ `ACK:LED_ON`
  * Header มีขนาดเพียง 8 ไบต์ และข้อความคำสั่งสั้น ESP32 ตรวจคำสั่งด้วย `strcmp()` ครั้งเดียว
* **HTTP RESTful** มีค่า RTT เฉลี่ย **52.64 ms** (Min 28.60 ms, Max 147.13 ms) และถ้าตัดรอบที่กระโดด (147.13 ms) ออก ค่าเฉลี่ยปกติอยู่ที่ประมาณ **42.14 ms** สูงกว่า UDP ประมาณ **8–9 เท่า** เพราะทำงานบน TCP
  * ต้องสร้างการเชื่อมต่อก่อน ทำให้เสียเวลาเพิ่มอย่างน้อย 1 RTT
  * HTTP Header มีขนาดหลายสิบไบต์ และต้องส่งทุกครั้ง
  * ESP32 ต้องพาร์ส HTTP Header จับคู่ URI และพาร์ส JSON ด้วย cJSON ก่อนสั่งงาน
  * ถ้าเรียกผ่านชื่อ `esp32-node.local` จะเสียเวลาค้นหาชื่อด้วย mDNS เพิ่มอีก
* **ค่า RTT สูงสุดที่กระโดดเป็นบางครั้ง** เกิดจาก ESP32 เปิดโหมดประหยัดพลังงาน Wi-Fi (`WIFI_PS_MIN_MODEM`) เป็นค่าเริ่มต้น ทำให้วิทยุหลับระหว่างรอบ DTIM ถ้าปิดด้วย `esp_wifi_set_ps(WIFI_PS_NONE)` ค่าจะต่ำและนิ่งขึ้น
* **สรุป** UDP ตอบสนองได้เร็วกว่า เหมาะกับงาน Real-time Streaming, Sensor Telemetry และคำสั่งควบคุมที่ต้องการความหน่วงต่ำ ส่วน HTTP เหมาะกับงานที่ต้องการความถูกต้องของข้อมูลและใช้งานกับเครื่องมือมาตรฐานได้ง่าย

2. รันสคริปต์ `udp_listener.py` เป็นเวลา 1 นาที จงบันทึกค่าและคำนวณอัตราการสูญหายของแพ็กเก็ต (Packet Loss Rate) พร้อมวิเคราะห์สาเหตุที่ทำให้เกิดการสูญหายบนเครือข่าย Wi-Fi
* **สูตรคำนวณ**
  $$\text{Packet Loss Rate} = \frac{\text{Lost}}{\text{Received} + \text{Lost}} \times 100\%$$
* **ผลการคำนวณ** ได้รับแพ็กเก็ต 574 แพ็กเก็ต, สูญหาย 26 แพ็กเก็ต คิดเป็น
  $$\text{Packet Loss Rate} = \frac{26}{574 + 26} \times 100 = \mathbf{4.33\%}$$
  * ที่อัตรา 10 Hz เป็นเวลา 1 นาที ESP32 ควรส่ง 600 แพ็กเก็ต ซึ่งตรงกับ Received + Lost = 574 + 26 = 600 (Seq 2051 ถึง 2650)
  * การสูญหายส่วนใหญ่เกิดเป็นช่วงติดกัน (Burst) เช่น หาย 6 แพ็กเก็ตติดกันที่ Seq 2345–2350 และ 4 แพ็กเก็ตที่ Seq 2493–2496 ซึ่งเป็นลักษณะของสัญญาณรบกวนหรือการชนกันชั่วขณะบน Wi-Fi มากกว่าการสูญหายแบบสุ่มทีละตัว
* **การทำงานของเซนเซอร์** ค่า Potentiometer เปลี่ยนแปลงตามการหมุนแบบ Real-time (จาก 0 ขึ้นไปถึงประมาณ 3,900 แล้วหมุนกลับลงมาที่ 0) ขณะที่ระบบยังส่งแพ็กเก็ตบรอดแคสต์ออกมาต่อเนื่อง การสูญหายของแพ็กเก็ตบางตัวจึงทำให้ค่าที่รับได้กระโดดข้ามไปบ้าง แต่ยังติดตามการเปลี่ยนแปลงได้
* **สาเหตุของการสูญหายบนเครือข่าย Wi-Fi**
  1. **ธรรมชาติของ UDP (Unreliable)** UDP เป็นแบบ "Fire-and-forget" ไม่รับประกันการส่งถึง ไม่ตรวจสอบการสูญหาย และไม่มีการส่งซ้ำ (No Retransmission)
  2. **Wi-Fi Broadcast ไม่มี ACK ที่ MAC Layer** บน IEEE 802.11 เฟรม Unicast จะได้ ACK และถูกส่งซ้ำเมื่อสูญหาย แต่ **Broadcast Frame** ถูกส่งครั้งเดียวโดยไม่รอ ACK จาก Client ใด ถ้าชนกันหรือมีคลื่นรบกวน แพ็กเก็ตจะหายทันที
  3. **ส่งด้วยอัตราข้อมูลต่ำสุด (Basic Rate)** Access Point ส่ง Broadcast ด้วยความเร็วต่ำเพื่อให้ทุกเครื่องรับได้ แต่ละเฟรมจึงใช้เวลาออกอากาศนานและเสี่ยงชนกันมากขึ้น
  4. **โหมดประหยัดพลังงาน (Power Save / DTIM)** AP เก็บ Broadcast ไว้รอส่งตามรอบ DTIM ถ้าบัฟเฟอร์ของ AP เต็ม หรือเครื่องผู้รับหลับอยู่ แพ็กเก็ตอาจหาย
  5. **สัญญาณรบกวนในย่าน 2.4 GHz** ย่านนี้มีความหนาแน่นสูงจาก Wi-Fi ข้างเคียง, Bluetooth และไมโครเวฟ ทำให้เกิดการชนกันของสัญญาณ (Collision) ได้ง่าย
  6. **บัฟเฟอร์เต็ม (Buffer Overflow)** ถ้า OS หรือสคริปต์ฝั่ง Client อ่านข้อมูลจาก Socket ไม่ทัน เช่น เพราะ `print()` ทุกแพ็กเก็ต แพ็กเก็ตใหม่อาจถูกดรอปทิ้ง


3. อธิบายข้อดีและข้อจำกัดของการใช้ `255.255.255.255` (UDP Broadcast) ในระบบ IoT และในสถานการณ์ใดที่ควรเปลี่ยนไปใช้ **UDP Multicast** หรือ **Unicast** แทน?
* **ข้อดีของ UDP Broadcast**
  * ส่งข้อมูลเพียงครั้งเดียว (1 Transmission) แต่อุปกรณ์ทุกตัวในวง LAN รับได้พร้อมกัน
  * ผู้ส่ง (ESP32) ไม่ต้องรู้ IP ของผู้รับแต่ละตัว จึงเหมาะกับการค้นหาอุปกรณ์ (Device Discovery)
  * ไม่ต้องมีเซิร์ฟเวอร์กลาง และเขียนโค้ดง่าย เพียงเปิด `SO_BROADCAST`
* **ข้อจำกัดของ UDP Broadcast**
  * ทุกอุปกรณ์ในเครือข่ายต้องตื่นมารับและประมวลผล แม้ไม่สนใจข้อมูลนั้น จึงเปลืองแบนด์วิดท์ พลังงาน และ CPU และเมื่ออุปกรณ์มากขึ้นอาจเกิด Broadcast Storm
  * ไม่สามารถข้าม Router/Subnet ได้ และเครือข่ายองค์กรหรือ Router บางรุ่นมักบล็อก Broadcast
  * บน Wi-Fi ไม่มี ACK และไม่มีการส่งซ้ำ จึงสูญหายง่ายกว่า Unicast ดังที่เห็นในข้อ 2
  * ไม่มีความปลอดภัย ใครอยู่ในวง LAN ก็ดักฟังข้อมูลได้
* **สถานการณ์ที่ควรเปลี่ยน**
  * **UDP Multicast (`224.0.0.0/4`, เช่น `239.x.x.x`)** ควรใช้เมื่อต้องส่งข้อมูลแบบ 1-to-Many เฉพาะกลุ่มอุปกรณ์ที่สนใจ (Subscribe Group ผ่าน IGMP) โดยไม่รบกวนอุปกรณ์อื่น เช่น มีหลายแดชบอร์ดดูค่าเซนเซอร์ชุดเดียวกัน
  * **UDP Unicast (ระบุ IP เฉพาะเจาะจง)** ควรใช้เมื่อส่งข้อมูลแบบ 1-to-1 ระหว่าง ESP32 กับเซิร์ฟเวอร์หรือ Gateway ตัวเดียว เพื่อลดภาระเครือข่าย และได้ประโยชน์จาก MAC-level ACK ของ Wi-Fi ทำให้สูญหายน้อยลง
  * **แนวทางที่ใช้ร่วมกันได้** ใช้ Broadcast เพื่อค้นหาอุปกรณ์ตอนเริ่มต้น แล้วเปลี่ยนเป็น Unicast หรือ Multicast เมื่อรู้ปลายทางแล้ว
