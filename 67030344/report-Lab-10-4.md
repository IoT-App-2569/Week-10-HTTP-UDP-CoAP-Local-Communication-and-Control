# ใบงานการทดลองที่ 10.4
## 1. การวิเคราะห์สัดส่วนข้อมูลตามมาตรฐาน (Architectural Byte Breakdown)
 
คำนวณขนาดข้อมูลของคำสั่งเปิดไฟ LED 1 ครั้ง (เฉพาะแพ็กเก็ต Request ไม่รวม IP Header 20 ไบต์ซึ่งเท่ากันทุกโปรโตคอล)
 
| รายการประเมิน | HTTP REST (POST) | UDP Datagram | CoAP (PUT) |
| :--- | :---: | :---: | :---: |
| **ชั้น L4 Transport** | TCP | UDP | UDP |
| **ขนาด L4 Header** | 20 ไบต์ | **8 ไบต์** | **8 ไบต์** |
| **ขนาด L7 Header** | 176 ไบต์ | **0 ไบต์** | 4 ไบต์ (ขั้นต่ำ) / 20 ไบต์ (ใช้จริง) |
| **Payload** | 15 ไบต์ (`{"state": true}`) | 6 ไบต์ (`LED_ON`) | 1 ไบต์ (`1`) |
| **ขนาดรวม** | **211 ไบต์** | **14 ไบต์** | **13 / 29 ไบต์** |
| **Payload Efficiency** | **7.1 %** | **42.9 %** | **7.7 % / 3.4 %** |
| **ส่ง 10,000 ครั้ง** | ≈ 2.11 MB | ≈ 140 KB | ≈ 130–290 KB |
 
 $$\text{Payload Efficiency Ratio} = \frac{\text{Payload Size}}{\text{Total Transmitted Bytes}} \times 100\%$$
 
**วิเคราะห์**
* UDP และ CoAP ใช้ข้อมูลน้อยกว่า HTTP ประมาณ **7–15 เท่า** และถ้านับแพ็กเก็ต Handshake/ACK ของ TCP ด้วย ส่วนต่างจะยิ่งมากขึ้น
* CoAP มี Efficiency ต่ำกว่า UDP เพราะ Payload มีแค่ 1 ไบต์ แต่ส่วนเพิ่มของ CoAP เป็นสิ่งที่ UDP ไม่มี คือ URI, Message ID และ Token สำหรับจับคู่ Request/Response
* ข้อมูลที่น้อยลงช่วยลดเวลาเปิดวิทยุ (Radio Airtime) จึงประหยัดแบตเตอรี่และค่า Data บนเครือข่าย NB-IoT/4G

## 2. การทดสอบวัดความหน่วงเวลา (RTT Latency & Jitter Benchmarking)
รันสคริปต์ `benchmark_protocols.py` บนคอมพิวเตอร์เพื่อทดสอบส่งคำสั่งควบคุมซ้ำจำนวน 50 รอบ
```bash
python3 benchmark_protocols.py --target 192.168.1.50 --protocol coap --rounds 50
```
### ตารางบันทึกผลการทดสอบ RTT (50 รอบ)
 
| โปรโตคอล | จำนวนรอบที่สำเร็จ | Packet Loss (%) | Min RTT (ms) | Mean RTT (ms) | Max RTT (ms) | Jitter / StdDev (ms) |
| :--- | :---: | :---: | :---: | :---: | :---: | :---: |
| **HTTP REST (`/api/led`)** | 50 / 50 | 0.0 % | 26.47 | 40.65 | 101.65 | 16.71 |
| **UDP Socket (`พอร์ต 3333`)** | 49 / 50 | 2.0 % | **2.14** | **5.91** | 24.49 | **4.87** |
| **CoAP PUT (`/actuator/led`)** | 50 / 50 | 0.0 % | 7.91 | 14.16 | 64.17 | 12.31 |
 
**วิเคราะห์ผล**
1. **UDP เร็วที่สุด** (เฉลี่ย 5.91 ms) และ Jitter ต่ำที่สุด เพราะไม่มี Handshake และไม่มีการประมวลผลระดับ Application แต่หายไป 1 รอบ (รอบที่ 24 timeout) เพราะไม่มีการส่งซ้ำ
2. **CoAP เร็วกว่า HTTP ประมาณ 2.9 เท่า** (14.16 เทียบกับ 40.65 ms) และไม่มีรอบที่หายเลย เพราะ `aiocoap` ส่งแบบ CON ซึ่งส่งซ้ำอัตโนมัติ ช้ากว่า UDP เล็กน้อยจากการเข้ารหัส/ถอดรหัส Option และการจัดการ Message ID ของ libcoap
3. **HTTP ช้าที่สุดและ Jitter สูงสุด** เพราะ `urllib` ส่ง `Connection: close` ทำให้ต้องเปิด TCP ใหม่และทำ Handshake ทุกรอบ แล้ว ESP32 ยังต้องพาร์ส Header ข้อความและ JSON
4. **รอบแรกของทุกโปรโตคอลช้ากว่าปกติ** (เช่น CoAP 64.17 ms) เพราะต้องทำ ARP หา MAC Address และเตรียม Context ครั้งแรก ส่วนค่าที่กระโดดเป็นช่วง ๆ เกิดจากโหมดประหยัดพลังงาน Wi-Fi ของ ESP32

## 3. การตรวจสอบการใช้หน่วยความจำบน ESP32 (RAM Footprint)
 
| สถานะการทำงานของ ESP32 | Free Heap (ผลจำลอง) | แรมที่ใช้ไปโดยประมาณ |
| :--- | :---: | :---: |
| **Baseline หลังต่อ Wi-Fi สำเร็จ** | ~ 247 KB | อ้างอิง (0 KB) |
| **UDP Socket Server** | ~ 241 KB | **~ 6 KB** |
| **HTTP REST Server (`esp_http_server`)** | ~ 209 KB | ~ 38 KB |
| **CoAP Server (`libcoap`)** | ~ 203 KB | ~ 44 KB |
 
**วิเคราะห์**
* **UDP** ใช้แรมน้อยที่สุด เพราะใช้แค่ Socket ของ LwIP และ Task ขนาดเล็ก
* **HTTP** ใช้แรมสำหรับ Task ของเซิร์ฟเวอร์, Connection Slot (ค่าเริ่มต้นรองรับได้ 7 Socket) และ Buffer สำหรับพาร์ส Header
* **CoAP (libcoap)** ใช้แรมมากที่สุด เพราะมี Task Stack 8 KB, Context, Resource Tree และหน่วยความจำสำหรับเก็บ PDU เพื่อส่งซ้ำแบบ CON

## 4. วิเคราะห์ผลและสรุปบทเรียนเชิงวิศวกรรม (Engineering Synthesis)
 
### 1. เปรียบเทียบจุดเด่นและจุดด้อย (Pros & Cons Matrix)
 
| โปรโตคอล | จุดเด่น | จุดด้อย |
| :--- | :--- | :--- |
| **HTTP** | ใช้กับเบราว์เซอร์และคลาวด์ได้ทันที, เครื่องมือมาตรฐานเยอะ (curl, fetch), TCP รับประกันข้อมูลถึง (Loss 0%), รองรับ HTTPS | ช้าที่สุด (40.65 ms), Jitter สูง (16.71 ms), ข้อมูลรวม 211 ไบต์ต่อคำสั่ง (Efficiency 7.1%), ใช้แรม ~38 KB |
| **UDP** | เร็วที่สุด (5.91 ms), Jitter ต่ำสุด, Overhead แค่ 8 ไบต์ (Efficiency 42.9%), ใช้แรมแค่ ~6 KB, Broadcast ได้ | ไม่รับประกันการส่งถึง (Loss 2%), ไม่มีมาตรฐานรูปแบบข้อมูล ต้องออกแบบคำสั่ง, ACK และความปลอดภัยเอง |
| **CoAP** | เร็วกว่า HTTP ~2.9 เท่า (14.16 ms), Loss 0% ด้วย CON, มี GET/PUT/POST/DELETE แบบ REST, มี Resource Discovery และ Observe | เบราว์เซอร์เรียกตรงไม่ได้ ต้องมี Proxy, ใช้แรมมากที่สุด (~44 KB), ต้องใช้ไลบรารีเฉพาะ (libcoap/aiocoap) |
 
### 2. กรณีศึกษาการตัดสินใจเลือกใช้โปรโตคอล (Engineering Case Studies)
 
#### กรณีศึกษาที่ 1: เซนเซอร์ความชื้นในดินและวาล์วน้ำ ใช้แบตเตอรี่โซลาร์เซลล์ ติดตั้งกลางแจ้งห่างไกล
* **โปรโตคอลที่เลือก:** **CoAP**
* **เหตุผลทางวิศวกรรม**
  1. **ประหยัดพลังงาน:** ข้อมูลต่อคำสั่งเพียงประมาณ 29 ไบต์เทียบกับ HTTP 211 ไบต์ และส่งได้ในรอบเดียวโดยไม่ต้อง Handshake โหนดจึงเปิดวิทยุสั้นมากแล้วกลับไป Deep Sleep ได้ทันที
  2. **เลือกความน่าเชื่อถือได้:** ใช้ **CON** กับคำสั่งเปิด-ปิดวาล์ว ซึ่งต้องสำเร็จแน่นอนแม้สัญญาณกลางแจ้งไม่ดี (ผลทดลอง Loss 0%) และใช้ **NON** กับค่าความชื้นที่ส่งเป็นระยะ ซึ่งค่าใหม่แทนค่าเก่าได้
  3. **รองรับเครือข่ายระยะไกล:** CoAP เหมาะกับ NB-IoT หรือ Thread ที่แบนด์วิดท์ต่ำและคิดค่าบริการตามปริมาณข้อมูล และใช้ Observe แจ้งเตือนเมื่อความชื้นเปลี่ยนได้โดยไม่ต้อง Polling
#### กรณีศึกษาที่ 2: เว็บแดชบอร์ดฝ่ายซ่อมบำรุงในโรงงาน เปิดผ่านเบราว์เซอร์บนแท็บเล็ต/สมาร์ตโฟน
* **โปรโตคอลที่เลือก:** **HTTP RESTful API (ควรใช้ HTTPS)**
* **เหตุผลทางวิศวกรรม**
  1. **เข้ากันได้ทันที:** เบราว์เซอร์รองรับ HTTP และ JSON ผ่าน `fetch()` โดยตรง ไม่ต้องติดตั้งแอปหรือ Proxy ส่วน UDP และ CoAP เบราว์เซอร์เรียกตรงไม่ได้
  2. **ความหน่วงยอมรับได้:** ผู้ใช้กดตั้งค่าไม่บ่อย RTT ประมาณ 40 ms เร็วพอสำหรับคน (มนุษย์รับรู้ความหน่วงได้ราว 100 ms ขึ้นไป) และ TCP รับประกันว่าค่าพารามิเตอร์ที่ตั้งจะถึงครบถูกต้อง
  3. **ความปลอดภัยและการดูแลระบบ:** ใช้ HTTPS และระบบยืนยันตัวตนมาตรฐานได้ อุปกรณ์ในโรงงานมีไฟเลี้ยงตลอด จึงไม่ต้องกังวลเรื่องแรม ~38 KB หรือ Overhead
#### กรณีศึกษาที่ 3: ควบคุมแขนกลอุตสาหกรรม ส่งพิกัด X, Y, Z ที่ 100 Hz ใน LAN ปิด
* **โปรโตคอลที่เลือก:** **UDP Socket (Unicast)**
* **เหตุผลทางวิศวกรรม**
  1. **ทันตามเวลา:** 100 Hz หมายถึงต้องส่งทุก **10 ms** UDP มี RTT เฉลี่ย 5.91 ms ซึ่งอยู่ในกรอบเวลา ส่วน HTTP (40.65 ms) ช้าเกินไป 4 เท่า ส่งไม่ทันแน่นอน
  2. **ข้อมูลใหม่สำคัญกว่าการส่งซ้ำ:** ถ้าพิกัดหายไป 1 แพ็กเก็ต อีก 10 ms ก็มีค่าใหม่มาแทน การส่งซ้ำแบบ TCP หรือ CoAP CON (รอ Timeout ประมาณ 2 วินาที) กลับทำให้ได้ค่าเก่าที่ไม่มีประโยชน์และทำให้ Jitter สูง
  3. **Overhead ต่ำและคาดเดาได้:** Header 8 ไบต์ และ Jitter ต่ำที่สุด (4.87 ms) เหมาะกับงานควบคุมแบบ Real-time ใน LAN ปิดที่มีสัญญาณรบกวนน้อย
  4. **ข้อเสนอเพิ่มเติม:** ใส่ Sequence Number และ Timestamp ในแพ็กเก็ต เพื่อทิ้งแพ็กเก็ตที่มาช้าหรือสลับลำดับ และควรใช้ LAN แบบสายหรือปิดโหมดประหยัดพลังงาน Wi-Fi เพื่อลด Jitter
