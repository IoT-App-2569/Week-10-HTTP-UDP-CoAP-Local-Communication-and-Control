## 4. บันทึกผลการทดลองและคำถามท้ายบท (Lab Report & Questions)
1. นำผลการ Query `/.well-known/core` มาแสดงในรายงาน พร้อมอธิบายรูปแบบ **CoRE Link Format (RFC 6690)** ว่าแสดงข้อมูลทรัพยากรอย่างไร
**ผลการ Query**
```text
</sensor/pot>,</actuator/led>
```
 
**CoRE Link Format** คือรูปแบบมาตรฐานที่ CoAP Server ใช้บอกว่าตัวเองมีทรัพยากรอะไรบ้าง Client แค่ส่ง `GET` ไปที่ URI คงที่ `/.well-known/core` ก็จะรู้รายการทรัพยากรทั้งหมด โดยไม่ต้องรู้ URL ล่วงหน้า
 
**โครงสร้างข้อมูล**
 
| ส่วนประกอบ | ตัวอย่าง | ความหมาย |
| :-- | :-- | :-- |
| `<URI>` | `</sensor/pot>` | path ของทรัพยากร อยู่ในวงเล็บแหลม |
| `,` | `</sensor/pot>,</actuator/led>` | คั่นระหว่างทรัพยากรแต่ละตัว |
| `;attr=value` | `</sensor/pot>;rt="sensor"` | คั่นเพื่อเพิ่มคุณสมบัติให้ทรัพยากร |
 
**Attribute ที่ใช้บ่อย**
* `rt` (Resource Type) ประเภทของทรัพยากร เช่น `rt="temperature"`
* `if` (Interface) รูปแบบการใช้งาน เช่น `if="sensor"`
* `ct` (Content-Format) ชนิดข้อมูล เช่น `ct=0` คือ text/plain, `ct=50` คือ JSON
* `title` คำอธิบายที่คนอ่านเข้าใจ
* `obs` บอกว่าทรัพยากรนั้นรองรับ Observe (RFC 7641)

2. อธิบายความแตกต่างของแพ็กเก็ต CoAP ระหว่าง **CON (Confirmable)** และ **NON (Non-confirmable)** เมื่อทดสอบในเครือข่ายที่มีการรบกวนสัญญาณ

| หัวข้อ | CON (Confirmable) | NON (Non-confirmable) |
| :-- | :-- | :-- |
| การตอบรับ | ผู้รับต้องส่ง ACK กลับ (Message ID เดียวกัน) | ไม่มี ACK |
| การส่งซ้ำ | ส่งซ้ำอัตโนมัติเมื่อไม่ได้ ACK แบบ Exponential Backoff (เริ่ม 2–3 วินาที แล้วเพิ่มเป็น 2 เท่า สูงสุด 4 ครั้ง) | ไม่ส่งซ้ำ หลุดแล้วหายเลย |
| เมื่อสัญญาณรบกวนสูง | ข้อมูลถึงปลายทางเกือบแน่นอน แต่ความหน่วงเพิ่มจากมิลลิวินาทีเป็นหลายวินาทีเมื่อต้องส่งซ้ำ | ความหน่วงต่ำและคงที่ แต่อัตราสูญหายเพิ่มตามระดับสัญญาณรบกวน |
| ภาระเครือข่าย | สูงกว่า (Request + ACK + แพ็กเก็ตส่งซ้ำ) | ต่ำที่สุด ส่งครั้งเดียว |
| การกันข้อมูลซ้ำ | ผู้รับใช้ Message ID ตัดแพ็กเก็ตที่ส่งซ้ำ ไม่ให้สั่งงานซ้ำสองรอบ | – |
| เหมาะกับ | คำสั่งควบคุมที่ต้องสำเร็จ เช่น `PUT /actuator/led`, เปิด-ปิดวาล์ว | ข้อมูลเซนเซอร์ที่ส่งถี่ เช่น ค่า Potentiometer ทุก 100 ms ซึ่งค่าใหม่แทนค่าเก่าได้ |

3. ทำไม CoAP จึงเหมาะสมกับโปรโตคอลการสื่อสารบนเครือข่ายเช่น Thread, Zigbee IP หรือ NB-IoT มากกว่า HTTP?
1. **Header เล็กมาก**
   * CoAP ใช้ Header แบบไบนารีขนาดคงที่เพียง **4 ไบต์**
   * HTTP ใช้ Header แบบข้อความ เฉพาะ Response ในแล็บ 10.1 ก็ยาว **71 ไบต์** แล้ว
   * Thread และ Zigbee IP ใช้ IEEE 802.15.4 ซึ่งมีเฟรมใหญ่สุดเพียง **127 ไบต์** CoAP จึงใส่ได้ในเฟรมเดียว ส่วน HTTP มักต้องแบ่งเป็นหลายเฟรม (Fragmentation) ซึ่งเสี่ยงหายมากขึ้น
2. **ทำงานบน UDP ไม่ต้องใช้ TCP**
   * HTTP ต้องทำ 3-Way Handshake และปิดการเชื่อมต่อ ทำให้เสียหลายรอบไป-กลับ
   * CoAP ส่ง Request และรับ Response ได้ใน 1 รอบ เหมาะกับเครือข่ายที่ช้าและมีความหน่วงสูงอย่าง NB-IoT
3. **ประหยัดพลังงาน**
   * โหนดที่ใช้แบตเตอรี่ตื่นขึ้นมาส่งแพ็กเก็ตไม่กี่สิบไบต์แล้วกลับไปหลับได้ทันที ไม่ต้องคงการเชื่อมต่อ TCP ไว้
   * จำนวนครั้งที่เปิดวิทยุน้อยลง แบตเตอรี่จึงใช้ได้นานหลายปี
4. **ความน่าเชื่อถือแบบเลือกได้** ใช้ CON กับคำสั่งสำคัญ และ NON กับข้อมูลที่ส่งถี่ ต่างจาก TCP ที่บังคับรับประกันทุกแพ็กเก็ต
5. **รองรับ Observe และ Multicast**
   * Observe (RFC 7641) ให้ Server ส่งค่าใหม่มาเองเมื่อข้อมูลเปลี่ยน ไม่ต้อง Polling ซ้ำแบบ HTTP
   * ค้นหาอุปกรณ์หลายตัวพร้อมกันด้วย Multicast ได้
6. **ยังเป็นแบบ REST เหมือน HTTP** มี GET/POST/PUT/DELETE และ Response Code คล้ายกัน จึงแปลงผ่าน Proxy เป็น HTTP ได้ง่าย เชื่อมต่อกับเว็บหรือคลาวด์ได้สะดวก
